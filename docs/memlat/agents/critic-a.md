- **kernel-mechanism#22**: Both verifiers: partly-correct. The order-0-or-PMD check is not in the map hypercall (it is in guest_get_valid_pte), and 'leaf size depends only on host backing' holds for the initial mapping only. Safe wording: [code; guest-side mechanism] At EL2, donation (protected VM) annotates the host stage-2 range page by page with owner = guest and maps the range in the guest table as RWX, state OWNED; sharing (non-protected VM) leaves host stage-2 untouched (vmemmap state SHARED_OWNED) and maps the range read-only as SHARED_BORROWED, a later write fault being resolved by pkvm_relax_perms without changing the granule. In both cases the guest mapping is one kvm_pgtable_stage2_map call over nr_pages and guest_stage2_force_pte_cb returns false, so 512 aligned pages become one 2 MiB block and a single page a 4 KiB entry. The order-0-or-PMD restriction is enforced in guest_get_valid_pte (relax, unshare, wrprotect, reclaim); the map hypercall itself does not validate nr_pages (the host only ever passes 1 or 512). The INITIAL leaf size therefore follows the host backing (4 KiB backing gives 4 KiB leaves; PMD-mapped THP with 2 MiB-congruent memslot alignment and no earlier 4 KiB mapping inside the block gives 2 MiB blocks), identically for protected and non-protected guests and identically in C and Rust (both call the C pgtable.c). It is not the only determinant afterwards: guest MEM_SHARE/UNSHARE splits the containing block, dirty logging re-maps at 4 KiB, and an already pinned page inside the 2 MiB range forces 4 KiB.

## Missing for root cause

- [64 MB random +3.25%; H, Figure 7] STATUS: a well-supported hypothesis (hardware two-stage translation on TLB misses when the host runs under stage-2 in protected mode), not yet a root cause. What is solid: it is a host-side number; the robust size is +6.5 ns (+3.5% by medians; the published +3.25% is a ratio of means that include 2 to 3 fast iterations per mode); only protected mode turns on HCR_EL2.VM for the host; host RAM is pre-mapped, so no EL2 software runs; the increment is absent up to 2 MB and flat from 8 MB. MISSING 1: a protected-versus-nvhe (ideally four-mode) comparison on ONE machine in ONE recorded platform state with PMU counters (cycles, L2-TLB refills, L2 and L3 cache refills per access, 0.5 to 64 MB), showing equal refill counts and a higher cost per refill. Today the mode difference comes from N90 timings of four separate boots without counters and the counters from the N80 in protected mode only. experiments/memlat-probe/run5-mode-compare.sh is staged for this and marked 'PROPOSED, NOT EXECUTED' (it still has the forward-only contiguity metric and the seed-outer loop criticised by the audit). At 64 MB itself the equal-count assumption is nearly harmless (the protected rate is 1.000 refill per access and cannot be exceeded); between 3 and 8 MB it is untested.
- [64 MB random] MISSING 2: a causal control in both modes. With the buffer on 2 MiB or 1 GiB stage-1 pages the TLB misses disappear; if the protected-minus-baseline increment disappears with them, the cost is in translation. Huge pages were measured on the N80 in protected mode only (8 MB: 82 to 88 ns against 100 to 107 ns).
- [64 MB random] MISSING 3: the facts the mechanism presupposes for the N90 itself: a raw dmesg of each boot mode (exception level, 'IPA Size Limit', pool line), /boot/config of 6.6.0-73-generic (C or Rust EL2; by the release history almost certainly the C EL2, which matters because the paper describes a Rust monitor), the host stage-2 leaf sizes for the benchmark's frames and page-table frames (the N90 kernel has no stage-2 dump; the block layout is a model on a D80F3 memory map), and a process list showing that no VM ran.
- [64 MB random] MISSING 4: separation from boot session and physical placement. There is one boot per mode (plus a second set without metadata). On the N80 the choice of frames alone moved the 64 MB random latency by 3.1 to 3.7% within protected mode (Exp F), the same size as the effect; newer unverified logs attribute that to stage-2 granularity next to the background VM, which, if confirmed, would not apply to an N90 host without a VM, but this has to be shown. The hypervisor pool also changes which frames the allocator hands out in protected mode. Needed: at least three boots per mode in randomised order with the buffer's PFNs logged, or a same-boot design.
- [64 MB random] MISSING 5: control of the platform state. The N90 has a fast and a slow memory-latency state unrelated to KVM mode (150 against 185 ns at 64 MB) whose cause is unknown and which was not recorded; the comparison must be repeated with the interconnect governor and frequency pinned and logged, and the increment shown in both states. The discarded first protected run (try1) cannot be re-examined because its raw data are gone.
- [64 MB random] MISSING 6: quantitative closure. Why the increment per refill is about 3.8 ns at 3 to 4 MB and 6.5 to 8.1 ns from 8 MB (a cross-machine quotient with a per-seed spread of 1.8 to 5.9), why sequential access exposes at most 0.1 to 0.4 ns, and what the 11.7 to 14.6 cycles consist of. This needs per-mode counts of walk-related cache refills or a description of the FTC862 walk caches; the reference counts 9 / 14 / 19 are architectural upper bounds only.
- [64 MB random] MISSING 7: an adversarial verification of the newest same-boot N80 experiments (S, V, V2, W, H). If they hold they are the first causal evidence that host TLB misses under pKVM read stage-2 descriptors and that the cost depends on stage-2 granularity, but they compare 4 KiB stage-2 leaves with block mappings on the N80 with the Rust EL2, not protected with non-protected boots on the N90, and the leaf size is inferred from the code.
- [64 MB random; wording of the reply] Figure 7 characterises 'N90 booted with pKVM enabled, trusted VM masked, kernel 6.6.0-73.76 (most likely the C EL2), core at 1.80 GHz'. If the reply or the revised paper attributes the number to the Rust monitor or to the deployed system with the x-kernel VM running, a re-measurement on a release with CONFIG_X1_RMS=y (6.6.0-76.85 or later) with the VM state recorded is required; with a VM running, host pages next to VM memory may cost more than the figure shows.
- [LLC boundary +3.55%; H, Figure 7] STATUS: as far as the data can tell this is not an effect of protected mode: it is the difference between 6 and 4 slow iterations out of 10 (p = 0.40; interval -4.2% to +11.1%), Figure 7 itself shows -3.02% against VHE, the sign flips with stride, and the second run set gives +0.65%. What is NOT known is the root cause of the two levels. MISSING 1: a record of what selects the fast (about 10.2 ns) or slow (about 12.4 ns) level per iteration on the N90: the interconnect frequency sampled per timed interval under the default governor, and runs with the frequency pinned (prediction of the open hypothesis: one level per frequency). No N90 interconnect state exists for June. The N80 cannot test it: it sat at a fixed 1800 MHz and never showed two levels (afternoon probes: a continuous 8.3 to 9.5 ns; lmbench in a newer unverified log: 10.16 to 10.51 ns over 16 sweeps).
- [LLC boundary] MISSING 2: the competing explanation has to be tested on the N90: physical layout of the buffer. On the N80 the virtual-versus-physical order of the same frames changes the 8 MB sequential latency by 8 to 11% (20% at contiguity 0.99) and the per-process layout explains most of its spread; this needs PFN and contiguity logging per iteration on the N90, with lmbench's own procedure (it rewrites the chain before every timed interval, which the afternoon probes did not).
- [LLC boundary] MISSING 3: statistical power to bound a protected-mode contribution: at least 30 iterations per mode over several boots in randomised order, or a paired within-boot design. Present bounds: 95% interval -4.2% to +11.1%; the random test allows at most 0.44 ns (3.9%) if every walk were fully exposed; the 12 to 64 MB rows show +0.1 ns.
- [LLC boundary] MISSING 4: an explanation of the differences among the stage-1-only baselines (the VHE boot is +6.8% above kvmoff on this row, p = 0.08, and +3.9%, +3.6% and +5.4% at 64 MB with strides 256, 512 and 1024, p = 0.011 and below 0.001, although both are the same translation regime by code). Until boot-to-boot effects of this size are understood, no 3% difference on a sequential row can be attributed to anything.
- [LLC boundary] MISSING 5: the row itself. 'LLC boundary (about 8 MB)' is sequential stride 256 at 8 MB; on the N80 the L3 refill counter rises from 3 MB, most page crossings already take an L2-TLB refill at 6 to 8 MB, and the run-to-run spread exceeds 3.55%. The reply should say that this row is not a usable overhead indicator as measured (report medians with dispersion, or replace the row) rather than offer a mechanism for +3.55%.
- [Figure 8; G, guest-side; neither reviewer number comes from it] The 'about 10 to 20% negative overhead above 10 MB' and the guest 'LLC boundary more than 10% lower' of the pVM series have no supported explanation other than a different platform state in that one run. Before anything is said about them the pVM set must be re-measured with the host kernel, host boot mode, VM type (crosvm flags), THP state, interconnect state and CPU frequency recorded and the ENV_TAG confirmed.
