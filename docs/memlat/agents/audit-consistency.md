# 核查报告：audit:consistency

## Summary

Audit of the eight reports against the raw lmbench reports, the N80 logs, klinux history and source, x-kernel commit 9bab5da3 and the paper extract.

The two central conclusions survive and are reproduced. The LLC-boundary +3.55 % is a mixture artefact (means 11.2029 and 11.6002 ns, exact permutation p = 0.3995). The 64 MB random +3.25 % reflects an increment of 6.5 to 8.1 ns per access that starts at 3 MB. No contradiction between reports changes either.

I list 23 contradictions. Ten are threshold, estimator, test or citation differences where every value reproduces once its rule is stated: slow-iteration counts 4/5/8/6, 4/5/7/6 and 4/5/6/5; fast-cell counts 16/9/6/5, 16/7/6/4, 16/7/6/5 and 15/7/5/4; per-walk costs; N80 correlations. Thirteen are substantive. The ones that change wording:

- EL2 implementation in June. prior-docs says the N90 ran the klinux Rust xhypervisor. Git says otherwise: CONFIG_X1_RMS=y entered a defconfig with commit b1b2979f0c0bf (written 2026-06-29, merged 2026-07-07, first release 6.6.0-76.85), and the measured kernel is 6.6.0-73.76, built 2026-05-15. The in-tree configuration builds the C pKVM EL2. The N90 config file itself was never recorded.
- Core clock. It was 1.80 GHz, not 1.9 GHz, so 7.05 ns is 12.7 cycles, not 13.4.
- Second-level TLB. N80 counters put it at 1024 to about 1280 entries, not 512 and not 2000.
- N80 background VM. A VM started at boot was running during every N80 measurement; no report knew. Walk counts are unaffected; N80 latencies and the contiguity explanation are not safe.
- Reasoning and labels. concl#6's argument against a per-DRAM-access cost is invalid. host-stats#10's claim that adjacent measurements are independent is contradicted (19 cells slow at both 8 and 12 MB against 12.5 expected, p = 0.0006). arch-literature's 9.9 % colour figure and lmbench-semantics' 53 % are different quantities under one label.

The paper's Figure 8 sentence disagrees with its own figure: only the two pVM series are negative, from 3 MB, by 17 to 32 %.

## Threats to validity

- NoC frequency-scaling explanation of the fast and slow states (concl#11, #12; host-stats#11, #19; lmbench-semantics#14; arch-literature#23; prior-docs#35). All cite the worklog or the driver source. No N90 file records any devfreq state. In the N80 logs the NoC frequency never varies (every sample is 1800000), so no data set tests it. The NoC driver also changed between the June kernel and the N80 kernel (443 lines at 6.6.0-73.76, 649 lines at 6.6.0-79.93; commit 466e8523ccf09 'Tune scaling with ramp-up and hysteresis', first in 6.6.0-75.80).
- The N80 governor is 'performance', attributed to the desktop power-management service. The policy table captured in devfreq-survey-n80.txt contains only simple_ondemand and powersave. trans_stat shows 54 transitions in the first 16.5 s and none afterwards. Who set the governor is not established.
- 'No VM on the N80' was repeated from the README by every report that used the device data. A VM started at boot was in fact running (vm-frames-n80.txt). Its crosvm command line is truncated in that file, so 'protected' rests on the VM name, the worklog and the Exp V slowdown, not on a recorded flag.
- 'No VM on the N90 during the host runs' rests on procedure only (scripts/apply-masks.sh masks and kills pvm-manage and crosvm). No result file records running processes. The same service started a VM unnoticed on the N80.
- 'One page walk per access with the same count in all modes' (kernel-mechanism#18, arch-literature#12, concl#4). Walk counts for lat_mem_rd exist only for the N80 in protected mode. The equality of counts between modes was measured only for munmap in June on another kernel tree. l2d_tlb_refill is used as a proxy for a page walk.
- 'Physical contiguity explains the two 8 MB values' (device#4, #5; lmbench-semantics#21; repeated as documented by host-stats#11, arch-literature#15, prior-docs#41). It was measured only on the N80, where the distribution is continuous (8.25 to 9.74 ns) and not two-valued, with the NoC pinned and with a background VM. Real lmbench on the N80 gives one level at 8 MB in 16 sweeps (10.16 to 10.51 ns). No pagemap data exist for the N90.
- N90 cache geometry (L3 8 MiB, 16 ways, 8192 sets) is taken from the N80 survey and the task text by host-stats#11, lmbench-semantics#16 and arch-literature#15. No N90 file records it. The N90 is a different SKU (maximum 2.1 and 3.1 GHz against 1.9 and 2.9 GHz).
- 'CPU locked at 1.9 GHz' is repeated from the run summaries and CONFIG.host by host-stats, kernel-mechanism, arch-literature, prior-docs and guest-fig8#15. The summaries record the requested maximum, and verify-clean-env.sh checks the reported value; the data show 1.80 GHz.
- THP=never and ASLR off during the N90 runs rest on prepare-host.sh. The summaries record only kernel, command line and requested CPU frequency. The 1 MB random latency in cycles supports 4 KiB pages indirectly.
- The benchmark pages of the N90 lying under 1 GiB stage-2 blocks (arch-literature#10 premise; kernel-mechanism#11 model). The model uses the memory map of a D80F3, a machine whose boot log reports a 48-bit IPA limit against 40 bits on the N90. The only stage-2 histogram is from the N80 under another kernel tree.
- The first protected-mode run (try1): every number (host-stats#20, guest-fig8#11, prior-docs#3, #6, #25, #30, #32) is quoted from documents. The documents themselves are not fully coherent: the 64 MB series switches at iteration 4, while the iteration durations in pkvm.md drop only from iteration 6.
- Conditions of the four guest runs: host mode, host kernel, crosvm options, pinning and THP are not recorded. The pVM data set carries the ENV_TAG of the NP run. kernel-mechanism#27 assumes kernel 6.6.0-73 for them.
- The N90 kernel configuration was never captured. The C-versus-Rust conclusion rests on the tree at the tag and on the build banner.
- Each mode is one boot per campaign. Iteration-level p-values treat iterations as independent although the slow state persists between consecutive children. Differences between boots without host stage-2 reach +6.8 % at the LLC-boundary point.
- N80 results are transferred to N90 across several differences at once: 1.90 against 1.80 GHz, 16 against 32 GB, Rust against C EL2, kernel 6.6.0-79 against 6.6.0-73, desktop session and background VM against a quiesced host.
