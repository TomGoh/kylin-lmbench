## Missing for root cause

- [Both numbers] A comparison of protected mode with a non-protected mode on one machine under a recorded platform state does not exist. The N90 June runs stored only kernel release, command line and scaling_max_freq (no PMU counts, no pagemap, no devfreq or THP state, no kernel config, no boot log); the N80 measurements of 2026-09-30 were taken in protected mode only (Rust EL2, kernel 6.6.0-79, interconnect pinned at 1800 MHz, an idle protected VM in the background). The script written for this, experiments/memlat-probe/run5-mode-compare.sh, is marked 'PROPOSED, NOT EXECUTED' and no modecmp output exists.
- [Both numbers] The EL2 implementation that produced the June 'KylinX' numbers: the tree default at tag 6.6.0-73.76 builds the C pKVM code (CONFIG_X1_RMS default n, enabled in the defconfig only on 2026-06-29), while the June documents and the paper describe the Rust hypervisor. The N90's /boot/config-6.6.0-73-generic, or a re-measurement on a kernel with CONFIG_X1_RMS=y, is needed before any explanation is tied to the measured binary or to the code in hyp/xhypervisor.
- [Both numbers] Replication at the level of boot sessions with the platform state pinned and recorded: there is one boot per mode per campaign, the protected column is a selected second run taken at midday 8 hours after the three night runs, the first protected run (fast state from iteration 4) was deleted, and the replicate campaign has no metadata. Needed: at least three boots per mode in randomised or interleaved order, each with /proc/cmdline, kernel config, boot log, all THP knobs, devfreq governors and frequencies, and scaling_cur_freq recorded.
- [Both numbers] The platform's fast and slow states are unexplained and are about five times larger than the protected-mode increment (random 64 MB about 150 against 185 ns; the 8 MB sequential cell low-only against two-valued). The interconnect-frequency hypothesis has one-sided, cross-machine support only: the N80 at 1800 MHz gives fast-level values from 16 MB up and a unimodal 8 MB cell, but at 3-8 MB its random latencies lie between the two N90 levels, no run at a lower or on-demand interconnect frequency exists on any machine (run4, run7 and run8 were not executed), and the N90's interconnect state was never recorded. Until this state can be read and set on the N90, neither number can be separated from it.
- [LLC boundary +3.55 %] What decides between the two values (about 10.4 and 12.4 ns) on the N90. No N90 run records the interconnect frequency, the physical page layout or PMU counts. Needed for the stride-256 8 MB cell in the quiesced environment: per child, the nocfreq frequency sampled at 100 ms or faster, pagemap frame numbers (contiguity, colour, number of 2 MiB regions) and cycles, l3d_cache_refill and l2d_tlb_refill per load; then a manipulation that makes the two values appear and disappear (governor pinned high, pinned low, simple_ondemand; the same frames remapped in sorted and shuffled order).
- [LLC boundary +3.55 %] The two-valued behaviour has not been reproduced under recorded conditions. On the N80 the cell is unimodal (lmbench: 10.16-10.51 ns in 16 sweeps; probe: a continuum of 8.25-9.74 ns that follows physical contiguity), so the contiguity result is not shown to be the N90 mechanism, and page-colour conflicts are excluded only on the N80.
- [LLC boundary +3.55 %] A bound on a genuine protected-mode effect at this cell. The interval is -4 % to +11 %, and a walk cost of the size seen in random access, paid once per 16 loads, would be +0.44 ns (+3.9 %), numerically indistinguishable from the observed +0.40 ns. Needed: about 108 iterations per mode (80 % power for 3.55 %), or a comparison conditioned on the state (levels within the low and within the high value over several boots), or cycles per load at equal walk counts from PMU data. At present the only argument against a walk cost of that size in sequential order is the 64 MB stride-256 cell (CI upper limit +0.22 ns), while the cells at 12-32 MB show +2 to +8 % against kvmoff and nvhe.
- [LLC boundary +3.55 %] An explanation of the carry-over (20 of 21 slow 12 MB cells follow a high 8 MB cell) and of the absence of the high value in the non-quiesced session (0 of 40 against 95 of 160). Reuse of freed pages by the next child and a platform state lasting a few seconds both fit; they can be separated only with the per-child logs described above.
- [LLC boundary +3.55 %] The source of the session-level variation that exceeds the pkvm difference: the 'vhe' boot is 6.8 % above kvmoff at this cell and 3.9-6.6 % above it at 12-64 MB although both run the host in the same translation regime (kvm-arm.mode=vhe is not a parsed value), and the excess does not recur in the standalone vhe session. As long as boots without stage-2 differ by more than the effect in question, 'not an effect of protected mode' is a statistical statement, not a root cause.
- [64 MB random +3.25 %] Counter evidence that the extra 6.5-8.4 ns (about 12-15 cycles at the inferred 1.80 GHz) is spent in page-table walks: on one machine in one platform state, protected against nvhe or kvmoff, with cycles, second-level TLB refills or table walks, and L1/L2/L3 accesses and refills per access, showing equal walk counts and extra cycles and cache accesses per walk. At present the per-walk reading divides N90 time differences by N80 walk counts, and the N80 has no non-protected measurement at all.
- [64 MB random +3.25 %] A manipulation that separates a cost per walk from a cost per memory access. The increment correlates with the N80 walk rate (r = 0.98) and with the N80 L3-refill rate (r = 0.95) almost equally, and from 16 MB both are one per access. Needed: a 2 x 2 design on one machine, (protected, non-protected) x (4 KiB, 2 MiB-backed buffer), at 16-64 MB: with huge pages the walks vanish while L3 misses stay at one per access, so a walk-related increment must vanish with them.
- [64 MB random +3.25 %] The host stage-2 configuration of the N90 during the runs: IPA size and number of stage-2 levels (40 bits appears only in excerpts in June documents), the block sizes that actually covered the benchmark's frames (no stage-2 dump), and whether anything had split the blocks (pvm-manage is said to have been masked, by procedure, not by record). Source code shows that the host stage 2 is pre-populated for all memory with blocks and enabled by __pkvm_prot_finalize; it does not show what the measured machine had.
- [64 MB random +3.25 %] A quantitative account of the size profile that is checked against counters: with the N80 walk counts the increment per walk is about 3.5-4 ns at 3-4 MB and 6.3-8.1 ns from 6 MB; it falls by about 0.8 ns from 8-32 MB to 48-64 MB; in sequential order it is below 1 ns per walk at stride 16 and cannot be attributed at strides of 64 and more. The N80 evening experiments V and V2 (pages whose host stage-2 mapping was split to 4 KiB against block-mapped pages in one protected boot: +8 to +20 ns per access from 6 MB with equal walk counts and more L2 refills, none at 2-4 MB) show that stage-2 descriptor reads cost time on a TLB miss, but they compare two stage-2 granularities and not stage 2 against no stage 2, rest on 2-8 measurements per split-page cell, were taken on another machine with the Rust EL2, and have not been independently verified.
- [64 MB random +3.25 %] Whether the increment persists in the fast platform state. Two pkvm cells (140.4 ns at 16 MB, 151.5 ns at 32 MB) sit 5-9 ns above the fast level of sessions without stage-2, but partly fast baseline cells cover the same values, and the medians of the deleted first protected run are documentary.
- [64 MB random +3.25 %] The statistical footing of the published figure. By the paper's estimator (difference of 10-iteration means) +3.25 % has exact permutation p = 0.093 and a CI of -0.4 % to +6.6 %; the robust effect (+6.2 to +7.1 ns, +3.4 to +3.8 %) rests on two protected boot sessions against six (permutation floor 1/28, or 1/16 respecting one protected session per campaign) and on leaving out two known fast-state sessions. 64 MB is also the size with the smallest relative overhead (+8.1 % at 6 MB, +6.3 % at 8 MB).
- [64 MB random +3.25 %] Microarchitectural facts for the FTC862 core (second-level TLB size, walk caches, whether combined stage-1 and stage-2 entries or stage-2-only entries are cached, prefetch behaviour) are documented nowhere in the sources, so the number of extra descriptor reads per walk cannot be derived; the conversion to cycles rests on an inferred clock, since no cycle counter was read on the N90.
- [Figure 8, because the reviewer names it] Both cited numbers are host-side Figure 7 numbers. Figure 8's negative overhead for the guest run labelled pVM is a fast-state run divided by normal-state runs. Missing: an alternation of pVM and NP guests inside one boot with the host state recorded, proof that the data set stored as pVM (ENV_TAG xkernel-pkvm-np) was a protected VM, and the guest build and crosvm options actually used.
