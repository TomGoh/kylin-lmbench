## Additional findings

- Label of the numerator dataset: every number called 'pVM' comes from results/xkernel-n90-pkvm-pvm-20260605-163040, but inside that directory the raw files are named xkernel-pkvm-np-cpu0-iterN.txt and autorun.marker / started.txt say ENV_TAG=xkernel-pkvm-np, the same tag as the NP run; CONFIG.xkernel.used (md5 40b058db...) and environment.txt (md5 19146876...) are byte-identical in all four guest directories. Nothing in the directory shows that the VM was protected, and no guest directory holds any host-side record (kvm-arm.mode, crosvm command, pinning, THP). The figure pipeline itself does not mix the two runs: build-vm-ratio-comparison.py parses each directory separately.
- The pVM guest is not faster than the fastest native level. Its median curve lies 2.0-14.0 ns above the noisy-host fast curve at every size 3-64 MB (+2.6/+5.2/+6.7/+13.9/+7.7/+7.0/+4.2/+4.0/+2.0/+2.8 ns), the same sign and size as the regular guests' offset above the clean host curve (+2.8..+14.2 ns). Figure 8's negative overhead is therefore a fast-state run divided by normal-state runs; with one run per VM type in one boot each, the data cannot tell whether protected VMs enter that state more often. The p = 1.08e-5 permutation values measure separation of two runs, not an effect of VM type.
- What made the 'noisy' host run noisy is not visible as CPU load in its own raw reports: the load average in the ten report headers is 1.00-1.08, the same as in the four clean runs (1.00-1.05). The visible differences are the Wi-Fi RX packet count at start (11906 against 340-400) and the +25% lat_tcp/lat_udp. The docs say pvm-manage was running; pkvm.md:77-80 describes that service as auto-starting a guest in pkvm mode. Whether a VM existed during this nVHE run is unrecorded, so the 'no guest' wording in the investigator's headline is not established.
- The 3-8 MB range is not strictly immune to the fast level on a clean host: standalone-pkvm.log run 10 has 8 MB = 104.11 ns against 120.0 (and guest VHE has 8 MB iteration 1 = 97.76). The '0/160' holds only for the four full host datasets, which weakens the investigator's open question built on 'never at 3-8 MB (0/280)'.
- The onset of the fast-state advantage differs between guest and host at 2 MB: the pVM set is 1.0-1.5 ns (4-6%) faster than all three other guest sets at 2 MB (p = 0.0007 against NP), whereas the noisy host is 0.35 ns slower than the clean host there. The host and guest fingerprints coincide from 3 MB up, not at 2 MB.
- Doc-versus-raw mismatch: standalone-memory-bench-validation.md:366 and pkvm.md:221 print the try2 64 MB value of iteration 10 as 191 ns; the raw file n90-pkvm-noLSM-try2-cpu0-iter10.txt (and the shipped CSV) has 178.793 ns, an intermediate cell. try2 therefore had two non-normal 64 MB iterations (6 and 10), not one.
- Mean-based ratios at 12-64 MB move by several points for reasons unrelated to VM type, because 3-6 of the 60 large-size cells in each regular guest set and 4-15 of 60 in each clean host set are sporadic fast or intermediate cells: for example pVM/nVHE at 24 MB is -16.7% on means and -20.2% on medians, and NP/nVHE at 24 MB is +3.6% on means and +0.75% on medians.
- Suggestive only, and it crosses data kinds (N80 device data against N90 guest data), so it is not a controlled comparison: results/memlat-n80-20260930/expH-rand.log (unmodified lmbench lat_mem_rd -t, THP off, interconnect governor 'performance' at 1800 MHz, 3 sweeps, host in protected mode, no VM) gives medians 28.1/34.7/62.6/101.2/131.7/142.3/147.9/149.6/150.8/152.5 ns at 3..64 MB. That is within 1.3 ns of the N90 pVM-guest curve at 3-4 MB and at 16-64 MB (29.0/36.0/.../141.2/147.2/150.2/151.1/152.9) and 32 ns below the N90 clean-host curve at 64 MB. It fits the still-unverified interconnect-frequency explanation of the fast state (worklog hypothesis H-i) and sits badly with the README's attribution of the N80-versus-N90 gap (about 155 against 185 ns) to the memory modules. The two machines also differ in L1 latency (2.107 against 2.223 ns), and the N80 logs contain only the 1800 MHz state, so no frequency dependence has actually been measured.
