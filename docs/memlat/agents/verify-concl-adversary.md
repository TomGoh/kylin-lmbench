## concl#6: partly-correct (confidence medium)

Claim under test: [reasoning] The random-access increment cannot be an extra cost per DRAM access: the 64 MB sequential test also fetches a new cache line from memory on every access (stride 256) and shows no increment of comparable size.

Statement that holds: [reasoning] At 64 MB the sequential stride-256 test fetches a new cache line from memory on every access and pkvm shows no increment there (+0.05 ns against kvmoff and nvhe, -0.12 ns against the three-baseline mean, versus +6.5 ns for random access). This rules out a cost added to every memory line fetch regardless of access pattern. It does not rule out a longer latency per isolated memory access: sequential fetches are prefetched and overlap (10.3 ns per load against about 185 ns for an isolated access), so added latency need not show. The same test would equally exclude the per-walk cost of claim 4: stride 1024 walks once every 4 accesses and shows +0.40 ns, i.e. 1.6 ns per walk instead of 6.3 to 8.1. The per-walk reading therefore rests on the size dependence, not on this comparison.

Evidence: Facts check out (host data, c5.py): stride 256 at 64 MB pkvm 10.345 ns vs kvmoff 10.357, nvhe 10.241, vhe 10.781; random 64 MB increment +6.497 ns. A 64 MB lap cannot stay in the 8 MiB L3, so each stride-256 load needs a new line from memory (N80 expD.log: event 0x2a about 0.986 per hop). The inference is the weak part. The per-load time of 10.3 ns is far below one memory round trip, so many fetches are in flight at once and an additive latency per fetch is hidden; only a throughput-type cost is excluded. Applying the claim's own logic to walks: N80 expD.log shows 0.25 walks per access at stride 1024 and 0.125 at stride 512; the N90 increments there (+0.404, +0.244 ns) correspond to 1.6 and 1.95 ns per walk, a quarter of the random-access figure. What does bear on the question (my own check, c4.py): the increment is already 7.05 ns at 8 MB, the same as at 12-64 MB (6.5-8.1), while the baseline latency at 8 MB is 112.5 ns against 185 ns at 64 MB, and a fit against the N80 walk rate leaves a residual of 5.9 against 16.7 for the N80 L3-refill rate. That favours walks over memory fetches but is not decisive, because the two rates rise together (0.84 and 0.79 at 6 MB, 0.97 and 0.88 at 8 MB) and the N80 refill counter reads 0.49 per hop at 4 MB sequential, where latency is 4.4 ns, so it is not a clean count of memory fetches.

- Host versus guest: both numbers in the reviewer's comment (3.55% and 3.25%) are host-side numbers from Figure 7 (N90 booted with kvm-arm.mode=protected, no VM running). Figure 8 is guest-side (lmbench inside the x-kernel VM under crosvm, stride 16 only, ratios pVM/nVHE, pVM/VHE, NP/nVHE) and contains neither number: there the data set labelled pVM is 20 to 32% faster in random access from 3 MB up, and sequential stride 16 is within about 1%. The reviewer's 'Figures 7 and 8' merges two different experiments; an answer about stage-2 page walks on the host does not explain Figure 8.
- Which EL2 code ran on the N90 is not what the worklog says. The N90 host reports identify the kernel as 6.6.0-73-generic #76, built 2026-05-15, which matches tag 6.6.0-73.76. At that tag CONFIG_X1_RMS is not set in any in-tree config (Kconfig default n; it first appears as =y in kylinos_generic_defconfig at tag 6.6.0-76.85), and arch/arm64/kvm/hyp/nvhe/Makefile line 11 then builds the C objects; the Rust code lived in arch/arm64/kvm/hyp/nvhe/rust, not xhypervisor. The N80 measurements of 2026-09-30 ran 6.6.0-79 with CONFIG_X1_RMS=y. Both variants pre-populate host stage 2, so the walk-rate argument is unaffected.
- The pkvm column of Figure 7 is a rerun. A first quiesced protected-mode run (try1) is described in docs/n90-kvm-host/standalone-memory-bench-validation.md section 9: 64 MB random access 194, 179, 194 ns in iterations 1-3, then about 154 ns in iterations 4-10. It was replaced by try2. The try1 raw files are not in the repository although two documents say they were kept, so nothing about try1 can be re-derived. The +7 ns increment does not depend on that choice: it is reproduced by the standalone rerun on separate boots.

In those sets protected minus non-protected at 8 MB is +3.8 ns against one baseline and -2.3 ns against another (baselines 78.5, 81.1, 84.6 ns), so they neither confirm nor refute the +7 ns increment.
- The fast-state signature is the same in the guest set labelled pVM (against the other three guests) and in the non-quiesced host set (against the quiesced host sets): random access 19 to 36% lower from 3 MB up, par_mem 17 to 27% lower at 4-33 MB, bw_mem 16 to 24% higher at 4-8 MB, and the 8 MB sequential point always at the fast level (guest pVM 9.87-10.15 ns in all 10 iterations). Figure 8's negative overhead and the paper's 'LLC boundary more than 10% lower' for the pVM (guest means -15.6% vs the nVHE-host guest, -11.0% vs the VHE-host guest) therefore compare two platform states, not two VM types. No host-side state was recorded for any guest run.
- New N80 logs appeared in the repository while I was verifying (commit 5cca9000, 18:45): expR.log and expBG.log. The NoC frequency reads 1800000 before and after every interval. With other cores streaming memory, 64 MB random access rises from 148-154 ns to 197, 247 and 335 ns and 8 MB random from 96 to 181-310 ns, so heavy background memory traffic at fixed NoC frequency slows the test and cannot be what made the non-quiesced N90 run faster. No experiment that changes the governor has been run.
- lmbench rewrites the pointer chain before every timed interval: src/lib_timing.c lines 757-759 call the initialize routine before start(0), and stride_initialize / thrash_initialize rewrite the chain because base_initialize returns early (src/lib_mem.c line 138) without clearing state->initialized. Every lmbench interval is therefore preceded by a burst of writes over the working set. The N80 probes used for expA-expF build the chain once; this matters for any argument about a traffic-driven governor and should be stated when N80 probe results are compared with lmbench results.
- Files referenced but absent at HEAD 5cca9000 of kylin-lmbench: docs/memlat/memlat-rootcause.zh-CN.md (named by the worklog as the authoritative conclusions), scripts/standalone-mem-bench.sh (named as the generator of results/standalone-mem-bench), and results/n90-day3-host/n90-pkvm-noLSM-try1-*.
- The PMU event 0x2a (l3d_cache_refill) on this core is not a clean count of fetches from memory: N80 expB.log and expL.log show about 0.48 per hop for sequential stride 256 at 4 MB, where latency is 4.4 ns. Conclusions that use it as 'accesses that go to DRAM' should be treated with caution; the walk counter 0x2d behaves as expected (1.0 per hop for random access from 16 MB, stride/4096 for sequential access).
