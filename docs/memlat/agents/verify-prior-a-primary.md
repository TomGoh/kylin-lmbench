## Additional findings

- The try1 run is not lost entirely. `git show a96a67d6:docs/findings-2026-06-03/lmbench-N10-4config-all-metrics.csv` holds try1 medians and MAD% for all 684 metrics (its three other columns equal the raw-CSV medians in 684/684 rows; commit 0bb79c41 calls it a stale try1 snapshot). This contradicts the bundle caveat 'Every try1 number in this report is quoted from the docs and cannot be checked'. It also allows a protected-vs-nVHE comparison inside the fast state: try1 minus nVHE-noisy medians are +1.1 / +7.1 / +6.2 / +4.0 / +4.3 ns at 4 / 8 / 16 / 32 / 64 MB (slow state, try2 minus clean nVHE: +1.6 / +7.0 / +7.7 / +7.9 / +6.7 ns). Different boots and days, medians only.
- The 'CPU frequency locked at 1.9 GHz' premise is off by 5.6% on the N90. In every run with scaling_max_freq = 1900000 (all day-3 runs and the day-2 nVHE run) the L1 load is 2.223 ns and lat_ops are integer cycle counts only at 1.80 GHz (L1 4.00, integer div 8.0, double add 2.0, float mul 3.0, double div 12.0 cycles; at 1.9 GHz they would be 4.22, 8.46, 2.11, 3.17, 12.67). Runs capped at 2100000 give L1 1.906 ns = 4.00 cycles at 2.10 GHz. Every ns-to-cycle conversion at 1.9 GHz in the docs and claims is 5.6% too high (6.2-6.9 ns is 11.2-12.4 cycles; the docs' '950 cycles' per 500 ns is 900).
- Kernel-tree framing: at the measured release tag 6.6.0-73.76 the Rust EL2 code is under arch/arm64/kvm/hyp/nvhe/rust/src; hyp/xhypervisor did not exist until commit daf0405c4301f (2026-06-30, 'rename nvhe rust runtime to xhypervisor'). Calling the June N90 kernel 'klinux (hyp/xhypervisor)' is anachronistic. The host.rs function positions are identical at the tag and at HEAD (375, 485, 1749, 1838, 1974, 2160, 2435) and match the line numbers quoted in the n90-kvm-host docs (host.rs:374, 1749, 1838, 1974); the mmap overview quotes different numbers (414, 1839, 1930, 2068, 2249, 2521) because it describes the 'common' tree.
- Provenance gaps in the standalone rerun, on which claims #1, #5 and #7 lean: scripts/standalone-mem-bench.sh is linked from three docs but was never committed (`git log --all` is empty for it), and results/standalone-mem-bench/*.log contain no date, kernel, cmdline, frequency or THP information. That these were separate boots, the exact commands, and the mode of each log rest on prose and file names only.
- Framing of claims #11 and #12: neither names machine or tree. The life-cycle split is Kaitian (THP always, ASLR 2, 6.6.30+ #637); the EL2 gate, op=3 histogram, dense control and threshold sweep are N80 (6.6.30xcore-stat+, 1.8 GHz); the D3000 anchors are a Great Wall D80F3 desktop at 2.5 GHz; all use the 'common' tree. None of the mechanism experiments ran on the N90 or on a 6.6.0-73 kernel.
- The June docs' sentence 'host RAM 99.5% 是 1G block' (c1-host-stage2-granularity.zh-CN.md:36, 191; c1-tlbi-threshold.zh-CN.md:34) is wrong as a statement about RAM: 99.5% refers to the 1 TiB IPA space. From the N80 /proc/iomem map, 17% to 37% of System RAM must be under 2 MiB or 4 KiB stage-2 mappings. The N80 probe logs show buffer frames starting at pfn 0x20ad820, inside the half-gigabyte 0x20a0000000-0x20bfffffff that cannot be a 1 GiB block, so part of the measured buffers there is 2 MiB-mapped at stage 2.
- Between-boot variation is as large as several 'significant' effects. The two protected boots (try1 from git, try2) differ by 3.1% on fork (134.83 vs 139.07 us) and 2.1% on page fault (0.2546 vs 0.2599 us); the noisy nVHE boot differs from the clean nVHE boot by -1.0% on fork and +2.2% on page fault. Exact permutation p-values over the 10 iterations of one boot (fork 1.1e-5, page fault 7.6e-5) therefore do not show a mode effect. For random 8 MB the boot-level picture is clean: six non-protected boots give medians 112.3-112.9 ns, two protected boots 119.6 and 120.0 ns.
- The state called 'fast' is not uniformly faster. In the all-fast nVHE-noisy run, against the clean nVHE run: random 4-64 MB -19% to -35% and bw_mem rd 8.39 MB +15.9%, but sequential 64 MB 11.11 vs 10.24 ns (+8.5%), bw_mem rd 67 MB 17103 vs 18404 MB/s (-7.1%), bzero 67 MB -13.0%. The pVM guest run, also all-fast, shows no sequential 64 MB penalty (10.28 vs 10.18-10.44 ns), so the streaming loss in the noisy run may be background load rather than the state. The 8 MB sequential point is unimodal-low in every all-fast data set (noisy 10.10-10.81, try1 median 10.014 with MAD 1.7%, pVM guest 9.87-10.15); its bimodality in the clean runs therefore tracks the same state variable, not only page placement.
- The paper's three host numbers reproduce as differences of 10-iteration means, try2 vs kvmoff: LLC boundary (stride 256, 8 MB) +3.55%, random 64 MB +3.25%, sequential 64 MB +0.29%.
