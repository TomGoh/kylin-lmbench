## Additional findings

- The x-kernel commit treated as 'the measured version' (9bab5da3, mainline) cannot have produced the three non-protected datasets. By code reading: platforms/aarch64-crosvm-virt/src/init.rs:11-21 calls kvm_guard_granule_init() unconditionally during boot (invoked from arch/khal/src/mem/mod.rs:49), and psci.rs:31-36 issues the MMIO_GUARD_INFO hypercall (0xC6000005) followed by assert_eq!(guard_has_range, 0x1). In klinux 6.6.0-73.76 that call is answered with (PAGE_SIZE, KVM_FUNC_HAS_RANGE) only for protected guests (arch/arm64/kvm/hyp/nvhe/pkvm.c:1601-1603, 1469-1480; Rust hyp/nvhe/rust/src/pkvm.rs:3463, 3282). For non-protected guests EL2 handles only HYP_MEMINFO and MEM_RELINQUISH (pkvm.c:1629-1644; Rust pkvm.rs:3516-3533) and the host handler denies the function (arch/arm64/kvm/hypercalls.c:77-105, 241-256, 281, 416-418: x0 = NOT_SUPPORTED, x1 = 0). An unmodified mainline image would therefore hit the assert when started as an NP guest or on an nVHE/VHE host. Branch origin/kylin100 of x-kernel (tip c87182db, committed 2026-05-08) replaces the assert by a conditional and boots both ways; it has the same CPU_NUM=2, round-robin task placement and 4 KiB anonymous mmap code, so the code conclusions of claims 13 and 18 are unaffected, but which build ran in each of the four guest runs is unknown. I did not boot anything to confirm this.
- The report header cannot show that the four guest runs used one guest build: 'Linux kylin-x 10.0.0 10.0.0' comes from constants in core/ksyscall/src/sys.rs (lines 36-38 at 9bab5da3, 85-87 on origin/kylin100). Only the identical MemTotal/MemFree in environment.txt speaks for a single image.
- The 'CPU frequency locked at 1.9 GHz' on the N90 is nominal. L1 load latency is 2.223 ns in all day-3 host runs, which is 4.00 cycles at 1.80 GHz (4.22 at 1.9 GHz); the same core gives 1.906 ns = 4.00 cycles at 2.1 GHz (N90 day 1) and 2.107 ns = 4.00 cycles at 1.9 GHz (N80). Integer divide (4.45 ns vs 3.81 ns at 2.1 GHz) gives the same ratio 2.1/1.8. Same-machine ratios are unaffected, but N80-versus-N90 absolute comparisons and any conversion of N90 latencies to cycles should use about 1.80 GHz.
- lmbench's random test (lat_mem_rd -t) does not use the first N pages of its buffer: src/lib_mem.c:146-152 builds a permutation over all 16384 pages of the 64 MB allocation and thrash_initialize (:254-270) uses its first npages entries. Every working-set size is therefore spread over the whole 64 MB of virtual address space (all 32 last-level page-table pages), with about 97% of hops leaving their 2 MB region at every size. Any explanation phrased in terms of '2 MB regions' or '512 pages' has to account for this; with 2 MB huge pages every size would touch all 32 huge pages.
- N80 device data collected later on 2026-09-30 (results/memlat-n80-20260930/expH-rand.log, expH-seq256.log, expH-noc-samples.log, still being appended until 19:15) run the unmodified lmbench lat_mem_rd with the interconnect devfreq device 'nocfreq' at 1800 MHz in all 17367 samples. With 4 KiB pages the random latency is 152.4-154.2 ns at 64 MB, 142.1-143.9 at 16 MB and 131.7-133.5 at 12 MB, which coincides with the N90 'fast state' (pVM guest 152.9/141.2/129.5; noisy nVHE host 150.1/134.2/121.8) and not with the N90 normal state (185.1/168.6/154.8). The 8 MB stride-256 point is unimodal at 10.16-10.51 ns in 16 sweeps, equal to the N90 low mode. With system THP the N80 gives 134.6-134.9 ns at 64 MB. This is circumstantial, cross-machine support for the fast state being a platform clock state (interconnect frequency) rather than large pages or page placement. No N80 run at a lower interconnect frequency exists and the N90 state in June was never recorded, so the hypothesis remains untested. These are (D) data and must not be merged with the N90 host or guest data.

THP and ASLR state, the current frequency and the devfreq (interconnect) governor and frequency were not recorded for any June run, host or guest.
