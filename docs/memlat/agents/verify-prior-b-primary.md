## Additional findings

- Cross-mode timing of lat_mem_rd on machines other than the N90 is sequential only: the D3000 anchor runs 'lat_mem_rd -P 1 -W 2 -N 5 64 128' (experiments/d3000-pkvm-apps/run-anchors.sh:39) and the Pixel runs '-P 1 -W 1 -N 3 64 128'; neither uses -t. The D3000 document's 'steady-state pointer chasing differs by about +/-1%' (recomputed: +0.57% at boot start, +0.18% at boot end) therefore agrees with the N90 sequential result and says nothing about the random-access overhead. The protected-mode random-access overhead has been measured on the N90 only.
- No primary record distinguishes the guest data set labelled 'pvm' from a non-protected VM: its started.txt and autorun.marker say ENV_TAG=xkernel-pkvm-np, its report files are named xkernel-pkvm-np-*, and its environment.txt is byte-identical to the np-clean and nvhe directories. All 10 of its iterations sit in the fast state at every size from 3 MB up (64 MB 152.2-155.5 ns), while the VHE, nVHE and NP guest sets show only isolated fast points (VHE iteration 1 at 8 MB 97.8 ns, iteration 2 at 12 MB 130.0; nVHE iteration 9 at 12 MB 134.9, iteration 10 at 16 MB 149.6). This matches the host pattern of a machine-level fast state, not a protected-VM effect.
- The noisy nVHE host run, which the docs use only for syscall and TCP contamination, is entirely in the fast state for memory latency: random 64 MB 149.9-151.9 ns (median 150.12 vs 185.05 in the quiesced nVHE run), random 8 MB 83.9 vs 112.6, and no slow mode at 8 MB sequential for any stride (0 of 50 points). The docs never looked at these columns.
- The standalone logs, which the docs present as the stable confirmation, also contain isolated fast points in all four modes: kvmoff random 32 MB run 6 = 151.3 and 64 MB run 9 = 169.5; vhe 16 MB run 10 = 134.5, 32 MB run 8 = 154.9; pkvm 16 MB run 3 = 140.4, 64 MB runs 7-8 = 181.3, 178.2.
- The QUICK-START re-run rule (lines 137 and 227-245) is asymmetric: it triggers a second run only for the protected mode, when that mode looks faster than or more than 10% away from VHE. The published protected column is the second of two attempts chosen after seeing the data; the first attempt's raw data are not in the repository or its history, and the baselines were not re-run although kvmoff has the most fast excursions (16/60).
- Inventory gaps in the investigator's framing: claims #19 and #24 describe all perf outputs as mmap_split_bench, munmap_only or op_sweep and miss the Pixel simpleperf outputs (munmap_only anon; MADV_DONTNEED single-page probe); claim #16 misses the second complete D3000 campaign (THP=always, 5 boot pairs) and the LMDB/Kaitian results. None of these changes the conclusion that no PMU or EL2 measurement exists for lat_mem_rd across modes.
- In the June perf outputs on FTC862, l2d_tlb_refill and the raw 0x34 DTLB-walk event agree within 1% (N80 21,658 vs 21,453; Kaitian 122,944 vs 122,556 and 123,609 vs 123,506). This supports using event 0x2d as the walk count in the 2026-09-30 N80 logs; the statement in experiments/memlat-probe/README.zh-CN.md:50 that FTC862 has no dtlb_walk event is true only of the named sysfs event.
- Above the 2 MB threshold, where the number of TLBIs is constant, the dense munmap gap still grows with the number of freed pages: N80 raw op-sweep +5.4, +14.2, +41.7, +73.8 us at 4, 8, 32, 64 MB (2.6-4.0%); Kaitian +6.2, +19.7, +178, +532 us (mean) at the same sizes. docs/mmap/c1-tlbi-threshold.zh-CN.md:156 attributes this to page-free memory accesses being slightly slower under stage-2, but nobody measured it. It is the only hint in the earlier mmap work of a per-access cost under host stage-2.
- D3000 application data are not uniformly small: besides the 0.3-3% throughput and wall-time penalties, RabbitMQ p99 at 85% of common capacity is 17-19% worse under protected mode in both campaigns (per-pair range +4% to +42%), so the data neither confirm nor cleanly contradict a '5-15%' figure; they are also from a different machine and kernel (6.6.30+ #2).
