## Additional findings

- Meaning of one cell: lat_mem_rd prints the MINIMUM of 11 repetitions measured inside one child process with one freshly faulted buffer per size (src/lat_mem_rd.c:143-149 benchmp + save_minimum; src/bench.h:198 TRIES 11; scripts/lmbench:473,477 pass no -N). 'Fast' therefore means the fastest repetition of that process was fast. The phenomenon is graded, not two-level: 21 of the 31 non-normal cells in the four clean host sets are intermediate (s 0.25-0.75), so 'fast state' is a simplification.
- The investigator's open question says the fast level never appears at 3-8 MB in clean runs (0/280). That is wrong at 8 MB: guest VHE 8 MB iteration 1 = 97.76 ns (fully fast, listed in claim 5 itself) and standalone pkvm host run 10, 8 MB = 104.11 ns (results/standalone-mem-bench/standalone-pkvm.log:50). Zero holds only for 3-6 MB.
- Machine identity check against an N80/N90 mix-up: all four guest datasets carry the N90 core-timing signature (L1 latency 2.225-2.226 ns, integer div 4.45 ns, double div 6.68 ns) equal to the N90 host files (2.223 ns, 4.45, 6.67) and different from the N80 (2.107 ns in results/memlat-n80-20260930/expH-rand.log). This matters because the N80's ordinary 64 MB random latency with its interconnect at 1800 MHz and huge pages off (152.4-154.2 ns, five sweeps in that log) coincides with the N90 'fast' level (150.1 noisy host, 152.9 pVM guest); the pVM dataset is nevertheless not an N80 dataset.
- A concrete host-side state that none of the June runs recorded: the kernel at tag 6.6.0-73.76 contains drivers/devfreq/phytium_noc.c, an interconnect (NoC) frequency driver whose default governor is simple_ondemand (line 307), polled every 100 ms (line 344), with load taken from four WR_NOLAST_HANDSHARK_NUM counters (lines 51-54). results/memlat-n80-20260930/devfreq-survey-n80.txt shows this device on the N80 with nine steps from 600 to 1800 MHz, 54 transitions in the first 16.5 s after boot, then governor 'performance', and a desktop power manager (ukui-power-manager) that owns a devfreq policy table. The June 'clean' environment masked desktop services. Whether the N90 had this device active and at which frequency during any host or guest run is not recorded anywhere, so this is a candidate for the physical nature of the normal/fast levels, not a finding; it was not measured at low frequency even on the N80.
- Primary-source corroboration that the noisy host run had a user desktop session: its raw report headers contain a gvfsd-fuse mount on /run/user/1000/gvfs in iterations 2-10 (and an extra tracefs mount), which is absent from all 40 iteration headers of the four clean host sets. docs/n90-kvm-host/pkvm.md:79-82 adds that in protected mode Kylin auto-starts pvm-manage.service, which launches a guest, unless it is masked.
- What the data cannot separate: there is exactly one pVM run; it was the first of the four guest runs, on a different day and boot (06-05 05:31-08:28 UTC by the guest clock; VHE 06-05 09:16-12:17, nVHE 06-06 02:30-05:30, NP 06-06 05:47-08:46), its ENV_TAG and file prefix are 'xkernel-pkvm-np' like the NP run (the label pVM exists only in the directory name), and it is the only guest set with perturbed pure-CPU metrics (integer div 4.45-4.61 ns against a constant 4.45 in the other three). 'Property of a protected VM' and 'host environment of that one run' are fully confounded. The claims justify 'this is not evidence of a pVM benefit'; they do not show that a pVM launched the same way would not be fast again. Only a same-boot alternation of pVM and NP with the host state recorded can settle it.
- Places where the host and guest fingerprints do NOT match, not listed in the claims: at 2 MB the signs are opposite (random: guest -5.8% with p = 7e-4, host +1.7% with p = 0.003; sequential strides 128/256: guest -2.2/-2.1%, host +0.8/+0.9%); sequential strides 512/1024 at 6 MB guest -15.6/-14.3% vs host -4.8/+2.9%, at 8 MB guest -17.1/-13.9% vs host +3.3/-8.9%; over all 230 sequential cells r is only 0.39 (0.13 for strides 512-1024). The match is strong for random latency, bw_mem, lat_ctx and sequential strides 64-256.
- The guest-over-host offset is preserved across the two levels, which is the strongest support for reading the pVM run as 'a guest on a machine in the fast state': pVM guest minus noisy host = +2.6,+5.2,+6.7,+14.0,+7.7,+7.0,+4.2,+4.0,+2.0,+2.8 ns; NP guest minus clean nVHE host = +2.8,+4.9,+13.3,+13.9,+9.9,+8.5,+8.5,+8.5,+9.0,+7.3 ns. Likewise pVM guest minus the documented try1 protected-mode host curve = +2.1,+4.1,+5.5,+6.8,+1.4,+0.8,-0.2,0.0,-0.1,-1.5 against NP guest minus try2 host = +2.1,+3.3,+8.1,+6.9,+3.1,+0.8,+0.3,+0.6,+1.9,+0.6 (try1 numbers are from docs only).
- Observation relevant to the reviewer's Figure 7 question, not covered by a claim: from 12 MB up the host booted in protected mode is 6.5-8.4 ns slower than KVM-off (medians), a VHE or nVHE guest is 4.8-10.2 ns slower than its own host, and an NP guest on a protected-mode host is only 0.3-3.1 ns slower than that host. One active stage-2 translation regime costs about 7 ns per random access at DRAM sizes whether it belongs to the host (protected mode) or to a guest.
