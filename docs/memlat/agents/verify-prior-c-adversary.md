## prior-docs#35: partly-correct (confidence medium)

Claim under test: D3 / Candidate cause of the two levels that the docs never considered (unverified): the klinux tree, which is the source of the Kylin 6.6.0-7x kernels, contains Phytium devfreq drivers for the SoC interconnect ('NoC') and the DDR memory unit, built as modules in the Kylin defconfig. The NoC driver uses the simple_ondemand governor by default with a 100 ms polling period and up-threshold 80, and its v1 load metric is read from a register named V1_WR_NOLAST_HANDSHARK_NUM (apparently write-channel traffic); the DDR driver used simple_ondemand until a 2025-05 commit made 'performance' the default for v1. The benchmark preparation script pins only CPU frequency, idle states, THP and ASLR, the clean-environment script masks about 100 services including upower and the display manager, and no run records devfreq state. A load-dependent interconnect or DDR clock would produce exactly a mode-independent slow level on a quiesced host and a fast level on a busy one, but whether the N90 exposes these devices and loads these modules is not recorded anywhere.

Statement that holds: Candidate cause, still unmeasured (the evidence leaves it open): klinux, the source of the Kylin kernels used (the N90 builds correspond to tags 6.6.0-52.51 and 6.6.0-73.76), contains Phytium devfreq drivers for the SoC interconnect (NoC) and the DDR memory unit, both built as modules in the Kylin arm64 defconfig. At both tags and at HEAD the NoC driver registers with the simple_ondemand governor, 100 ms polling, up-threshold 80 and down-differential 10; its v1 load metric is the peak of four counters read at offset 0x44 (WR_NOLAST_HANDSHARK_NUM; the V1_ prefix exists only at HEAD), which the driver comment at tag 6.6.0-73.76 describes as the peak number of DMU read/write commands on the AXI bus, so 'write-channel traffic only' is not supported. The DDR driver used simple_ondemand from 2024-07 until commit 3b3abf3c26ee2 (2025-05-07) made 'performance' the default; that commit is in both measured tags, so by kernel default the DDR clock was not load-dependent during the N90 measurements and only the interconnect remains a candidate. prepare-host.sh sets only CPU governor and frequency, idle states, THP and ASLR; apply-masks.sh masks 90 system and 12 user services including upower and lightdm; no N90 run records devfreq state, and whether the N90 loads the NoC module is not recorded. ## Additional findings

- The 'fast state' is not uniformly faster. In the non-quiesced N90 host run, sequential stride-256 latency at 12-64 MB is 3.6-8.5% higher than in the clean nVHE run, bw_mem_rd at 33.55/67.11 MB is 6-7% lower and bw_mem_bzero at 8-67 MB is 9-13% lower. The N80 lmbench sweeps show the same elevated stride-256 values at 12-24 MB (10.9-11.4 ns against 10.7-10.9 ns in the N90 clean runs); the pVM guest does not. Any explanation of the two states has to cover this.
- The raw reports show what 'noisy' means: load average is the same as in the clean runs (1.00-1.08), but the non-quiesced run has a gvfsd-fuse user mount (desktop session) in 9 of 10 reports and tracefs mounted on /sys/kernel/debug/tracing in 10 of 10, neither present in any of the 40 clean reports. The day-1 and day-2 fast data sets also show the gvfsd-fuse mount. The difference is a service/desktop configuration difference, not CPU load.
- The benchmark harness records only kernel release, command line and cpu_max_freqs (K/bench.sh:49-54). THP setting, governors, devfreq state and process lists are not recorded for any N90 run, so 'THP=never' in the non-quiesced run is an assumption (prepare-host.sh sets it together with the frequency).
- The nominal '1.9 GHz lock' on the N90 corresponds to 1.80 GHz effective: L1 load latency is 2.223 ns, integer add 0.28 ns, integer divide 4.45 ns and double add 1.11 ns in every day-3 report, i.e. 4, 0.5, 8 and 2 cycles of 0.5556 ns. The N80 runs at 1.90 GHz (L1 2.107 ns) and the day-1/day-2 N90 runs at 2.10 GHz (1.906 ns). Cycle conversions and cross-machine comparisons of cache-resident latencies should use these values.
- Page-fault latency also moves with machine state: the non-quiesced nVHE run is 2.1% above the clean nVHE run (0.2604 vs 0.2550 µs, p = 0.00001), the same size as the paper's +1.99% for protected mode; the documented try1 protected run showed no increase (0.2547), try2 and the standalone rerun show +2.0% and +1.1 to +1.4%.
- In the documented try1 run the random-latency switch to the fast level happened at iteration 4, but the iteration times stay long for iterations 4 and 5 (616 and 610 s) and drop only from iteration 6 (pkvm.md:110-112, 219-221), so iteration time and random latency did not switch together.
- Paper line numbers cited in claims #36-#39 are five to six lines off: P147-P151 are at paper.txt lines 214-218, P161 at 229, P167 at 235. The paragraph ids and quotations are correct.
- The day-2 default-mode lsm=ksaf data set (n90-baremetal-N5) is split across 12 hours on one boot: iterations 1-3 on 2026-06-01 21:03-21:11, iterations 4-5 on 2026-06-02 08:56-09:00 (uptime 11:53), with iteration 5 grossly disturbed. It should not be used as a baseline without that caveat.
- No host/guest or N80/N90 mix-up was found in these claims: cross-set comparisons (#30, #32) and N80 numbers (#39e, #41, #42) are labelled as such. The documented EL2-cycle result and the stage-2 block-size result come from the N80 with kernel 6.6.30xcore-stat+, a different tree from klinux.
