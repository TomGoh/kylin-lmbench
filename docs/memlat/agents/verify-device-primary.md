## Additional findings

- Data-kind check (the user's requirement to keep VM-internal and host experiments apart): all eight device claims rest on kind D only. The programs ran as ordinary host processes on a Great Wall N80F3 (hw-survey-n80.txt:5), booted with kvm-arm.mode=protected, on 2026-09-30. None of this was run on the N90 host (kind H, Figure 7) and none inside an x-kernel guest (kind G, Figure 8). The run scripts (run_all.sh, run2.sh, run3.sh) start no VM; that no VM was running in the background is stated in the README but recorded in no primary file (no process list), so that part is unverifiable. Because only protected mode was measured, D cannot by itself show any protected-versus-baseline difference, and it says nothing about guest behaviour.
- Cross-machine framing risk, verified in git: the N80 ran 6.6.0-79 #93 (klinux tag 6.6.0-79.93, 2026-09-02) with CONFIG_X1_RMS=y, i.e. the Rust EL2 in arch/arm64/kvm/hyp/xhypervisor. The N90 host data were taken on '6.6.0-73-generic #76-KYLINOS SMP Fri May 15 2026' (header of results/n90-day3-host/*-iter1.txt, identical in all four modes), which matches tag 6.6.0-73.76. At that tag X1_RMS is 'default n' (arch/arm64/kvm/Kconfig:76-79) and nothing in the tree sets it (git grep X1_RMS 6.6.0-73.76 finds only the Kconfig and hyp/nvhe/Makefile); CONFIG_X1_RMS=y first appears in kylinos_generic_defconfig at tag 6.6.0-76.85 (2026-07-07, commit b1b2979f0c0bf). The Rust sources existed in June under hyp/nvhe/rust but are compiled only when X1_RMS is set (hyp/nvhe/Makefile:11-132 at that tag). The benchmark repo records no kernel config for the N90 runs. Unless the N90 image was built with a non-default config, the paper's June numbers were measured with the C EL2, while the N80 measurements used the Rust EL2 on a kernel three months newer. This does not change TLB-refill counts with 4 KiB pages, but it undermines any statement that equates the N80's protected-mode behaviour with the paper's 'KylinX'.
- Exp F (device#6) is not a null result, and 'below 4%' should not be paraphrased as 'placement does not matter'. The 21 runs form two reproducible clusters: scatter and region:1 at 160.2 to 161.1 ns (6 runs), the other five policies at 154.5 to 157.2 ns (15 runs), with a gap of at least 3.07 ns while within-policy run-to-run ranges are at most 1.95 ns. The cluster means differ by 3.06% and the extreme policy means by 3.68%, which is the same size as the 3.25% effect the paper has to explain. The slow cluster has more L2-cache refills per access (ev17 1.37 to 1.41 against 1.16 to 1.21; Pearson r between ns_med and ev17 is +0.955, n=21), while L2 TLB refills (0.993 to 1.000) and L3 refills (0.997 to 1.000) are the same everywhere. Extra cache-line fetches at an unchanged data-miss rate point to page-table-walk memory accesses rather than DRAM location, but with only protected mode measured it cannot be told whether this is specific to stage 2. Untested hypothesis, not a finding.
- Design confound in Exp F: the 'scatter' policy takes exactly every 16th frame of the PFN-sorted pool (frames.c:231-232 with pool_pages 262144 and 16384 pages). One L2 way is 16 pages and one L3 way is 128 pages, so inside any physically contiguous stretch all selected frames share one L2 colour and only 8 of 128 L3 colours. frames.c logs no colour statistics, so the scatter slowdown cannot be attributed to physical spread. This does not explain region:1, which is contiguous (contig 0.993) and equally slow.
- Walk rates were measured in protected mode only. Their use for dividing N90 increments (kind H) into 'ns per walk' assumes the same rate in the other modes; experiments/memlat-probe/README.zh-CN.md:88-90 itself calls this 'expected'. At 16 MB and above the rate is saturated at 1.000, so the assumption is harmless there. Between 2 and 8 MB it is not tested, and the N80 rates there also vary strongly by seed (per-seed means 0.026/0.040/0.071 at 2 MB, 0.137/0.180/0.254 at 3 MB, 0.340/0.478/0.522 at 4 MB), so per-walk costs quoted for 2 to 4 MB carry an uncertainty of tens of percent.
- 'One page walk per 4 KiB page crossing' is an upper bound that most but not all sequential runs reach: across the 60 sequential 64 MB runs (expD, expB, expT), 8 show 2% to 6% fewer L2 TLB refills than page crossings and none shows more. Cause not determined.
- The NoC devfreq state was recorded once, at 17:24:12, after all experiments. The file header refers to a 'note on trans_stat' that exists nowhere in the repo. The power-manager policy table in the same file (devfreq-survey-n80.txt:103-127) contains only simple_ondemand and powersave, so the README's attribution of the 'performance' governor to the desktop power manager is not supported by the recorded data; who set it is unknown. My reading of trans_stat against the kernel source supports that the governor did not change during the runs (see device#8).
- The N80 environment differs from the N90 host runs in ways that matter for layout experiments: system THP is 'always' (hw-survey-n80.txt:79; buffers use MADV_NOHUGEPAGE), a desktop session was running with load 0.2 to 2.0 (meta.log), LSM and audit were on (cmdline line 17), against THP=never, lsm= and audit=0 on the N90. Page migration during Exp L (3 of 27 runs) is consistent with compaction activity on such a system. The contiguity distributions seen on the N80 should not be assumed for the N90.
- N90 hardware identity is not recorded in the N90 raw results: the lmbench headers give only 'MOTHERBOARD: Phytium D3000M', 8 processors, 1900 MHz. 'Same core type as the N80' (MIDR 0x700f8620) therefore rests on documents, not on primary data in results/n90-day3-host.
