## ek#4: refuted (confidence high)

Claim under test: Nothing merges the host stage-2 back into blocks: when a guest page is returned to the host (__pkvm_host_reclaim_page and VM teardown), the page is mapped again for the host as a 4 KiB leaf inside the existing last-level table. The fragmentation of the host stage-2 map caused by a protected VM therefore persists after the VM is gone, until reboot (apart from wholesale unmapping when the host stage-2 page pool is exhausted).

Statement that holds: The host stage-2 is merged back into blocks. When a guest or hypervisor page is returned to the host (__pkvm_host_reclaim_page at VM teardown, __pkvm_guest_relinquish_to_host, __pkvm_hyp_donate_host), host_stage2_set_owner_locked(..., PKVM_ID_HOST) maps it with kvm_pgtable_stage2_map, whose walker also runs a table-post callback, stage2_coalesce_walk_table_post (active once kvm_protected_mode_initialized is enabled at the end of boot). The page is first written as a 4 KiB default leaf in the existing last-level table; as soon as that table holds no other non-host entry (refcount 1) it is replaced by a 2 MiB block, and a level-2 table left without tables or annotations is replaced by a 1 GiB block (a 2 MiB return replaces the table directly). The fragmentation caused by a protected VM therefore does not persist until reboot: after teardown the host stage-2 returns to its boot-time shape, except for (i) tables that already existed at the end of EL2 initialisation, which pin_host_tables pins (hypervisor pool, memory-region boundaries), and (ii) regions that still hold a page owned by the hypervisor or another guest (for example EL2 heap pages, which come back only through the shrinker). The pool-exhaustion path drops only unpinned tables outside memory regions and is not what restores RAM blocks.

## Additional findings

- ek#4 is wrong and should not be used. The kernel at both tags contains eager coalescing of the host stage-2 (commit 7517d3cbbaf91, pgtable.c:1127-1176), which I confirmed by running the kernel's own page-table code in user space: after all donated pages are returned the table structure is identical to boot (0 extra table pages). The claim describes what happens only if kvm_protected_mode_initialized were never enabled (my counterfactual run reproduces it exactly).
- Consequence for the statement in docs/memlat/memlat-rootcause.zh-CN.md section 3.7 line 364 (Figure 7 unaffected because pvm-manage was masked and crosvm killed, scripts/apply-masks.sh:52,147-148): per the code this holds even if a protected VM had been started earlier in that boot and then killed, because teardown re-merges the blocks. The small residue is EL2 heap pages for VM metadata, which stay hypervisor-owned until the host shrinker reclaims them (pkvm.rs:2410-2425, arch/arm64/kvm/arm.c:2467-2478, pkvm.c:1256-1282). Under ek#4 as written that statement would have been unsafe.
- The boot-time host stage-2 is not all 1 GiB blocks even with no VM, and this part is permanent: every table existing at the end of __pkvm_init_finalise is pinned by pin_host_tables (setup.c:260-281; setup.rs:390-409). On the N80 map the harness gives 53 table pages at boot with only the hypervisor pool modelled: slots 0x80000000, 0xc0000000, 0x2080000000 and 0x2340000000 are level-2 tables, and four 2 MiB regions at unaligned region boundaries are 4 KiB-mapped. In addition the hyp text, data, rodata and bss inside the kernel image, the per-CPU hyp areas and pvmfw are EL2-owned (setup.c:124-176) and split their surroundings to 4 KiB; their positions are not in the logs. With the VM's pages in slots 0x82-0x8a, at most slots 0x22c0000000 and 0x2300000000 could still have been 1 GiB blocks during the N80 measurements, so the 'clear' class of experiment V is essentially 2 MiB blocks, not 1 GiB blocks.
- The region list from vm-frames.py is an imperfect proxy for 'host stage-2 split to 4 KiB' in both directions. It misses regions split by EL2-owned metadata pages (ek#3). It also includes regions whose present pages are not guest-owned: pages only touched by the VMM, and pages a protected guest shared back with the host (host_complete_share -> __host_set_page_state_range -> host_stage2_idmap_locked with default protection, host.rs:1329-1341, 1395-1406), which are valid default leaves and let the region coalesce back to a 2 MiB block once no annotation remains. Both errors dilute a shared-versus-clear contrast, so a measured difference is if anything an underestimate. Neither can be quantified from the recorded data.
- Everything in this bundle is derived from source (and from executing that source in a harness); no N80 log shows host stage-2 entry sizes, and the device has no interface to dump the EL2 tables. The two switches the conclusions depend on are KVM_PGTABLE_S2_PREFAULT_BLOCK in the host table flags and the static key kvm_protected_mode_initialized (enabled at arch/arm64/kvm/pkvm.c:489 before the host stage-2 is switched on). Both follow from the source; neither was observed on the device.
- The premise in ek#6 that the Rust EL2 is a transliteration of the C EL2 should be dropped. It is a port of a different arrangement of the same logic (transition structure, MMIO pre-population at boot, different abort handler, its own __kvm_pgtable_stage2_init). The equivalence that matters for the paper holds for a narrower reason: all host stage-2 updates go through the shared C pgtable.c with the same flags and callbacks, and that file is byte-identical at 6.6.0-73.76 and 6.6.0-79.93. The N90's actual kernel config is not in results/n90-day3-host, so 'C EL2 on the June N90' rests on the tag's defconfig.
- The suggestion that 2 MiB-backed guest memory removes the host-side cost is only partly supported by the code: the 2 MiB path requires the VMM to map the memory with PMD blocks (get_user_mapping_size), a 2 MiB donation still replaces the 1 GiB block of its slot and costs a last-level table of 512 annotations, and the order-0 memcache and page-table pages donated to EL2 still split other regions to 4 KiB. For non-protected guests under pKVM guest memory is shared without touching the host stage-2 (state kept in the hyp vmemmap, host.rs:1395-1406, mem_protect.c:971-984), but their memcache pages are donated all the same.
- Limits of my check: the harness replaces the allocator, TLB invalidation, locking and the hyp vmemmap with shims and models only the hypervisor pool as EL2-owned memory; hyp_memory was reconstructed from the top-level lines of iomem-n80.txt; the Rust wrappers were read but not executed; a 40-bit IPA (3-level host stage-2) was assumed from the boot log 'IPA Size Limit: 40 bits'.
