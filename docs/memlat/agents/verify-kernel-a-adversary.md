## Additional findings

- Data-kind check for this bundle: all 14 claims are HOST-side mechanism statements (Figure 7 side). None of them uses data measured inside the x-kernel guest (Figure 8). The empirical inputs they and I used are of four different origins that must not be merged in the paper text: (a) N90 host CSVs of June 2026 (kernel 6.6.0-73-generic, no VM); (b) N80 runs of June 2026 on kernel 6.6.30xcore-stat+ with the Rust EL2 (EL2 cycle gate, host stage-2 histogram; docs/mmap and results/n80-munmap-gate-c0) - these are neither N90 data nor part of the 2026-09-30 N80 set; (c) the N80 survey of 2026-09-30 (kernel 6.6.0-79 #93, CONFIG_X1_RMS=y); (d) dmesg files of a Great Wall D80F3 desktop running a non-klinux kernel 6.6.30+.
- Kernel-tree provenance gap not addressed by the investigator: two tags in klinux would produce uname 6.6.0-73-generic. Tag 6.6.0-73.76 (klad-v11 line) has the eager host stage-2 (prepopulate_host_stage2, PREFAULT_BLOCK, pin_host_tables). Tag 6.6.0-73.0.ok2604 (openKylin line, based on 6.6.132) has upstream-style pKVM with a LAZY host stage-2 and none of these three. The N90 boot lines quoted in docs/n90-kvm-host (pkvm.md:58, nvhe.md:37, vhe.md:37) say 'nv: 477 coarse grained trap handlers'; ARRAY_SIZE(encoding_to_cgt) is 477 in the klad tags (65.65, 66.66, 73.76, HEAD; the raw N80 log also prints 477) and 499 in 6.6.0-73.0.ok2604. So the quoted logs point to the klad tree, where the code reading applies; this rests on quoted, not raw, N90 logs (script tree_provenance.sh).
- Error in claim 9 that also affects the scenario count of claim 11: hyp stacks are not made hyp-owned in the host stage-2 (they are mapped only in the EL2 private range; fix_host_ownership walks the linear map), while a pvmfw image is (setup.c:162-176). In the June kernel pvmfw.bin is loaded into buddy-allocated pages at init (tag arm.c:2818-2907, 2934), so on a machine that ships pvmfw one more block region is split at boot.
- The D80F3 is not an 'N90-class' machine beyond the core MIDR: it logs a 48-bit IPA limit, has two L3 domains and 2.5 GHz cores, and runs a different kernel tree (6.6.30+, log prefix 'X [n]:', no 'nv:' line). Its memory map is therefore a stand-in. A better anchor exists in a primary log: the pool-size formula with the same low-memory layout and a 14 GiB high region reproduces the raw N80 line 'Reserved 86 MiB at 0x237a800000' exactly (pool_n80_check.py), which supports the layout style (about 2 GiB at 0x80000000 plus the rest at 0x2000000000) for the D3000M laptops.
- vhe and kvmoff are the same translation regime by code, yet in the N90 host CSVs 72 of 684 rows (10.5%) differ by more than 3% between them, including 31 of 230 sequential lat_mem_rd_load rows, against 21 rows (3.1%) for nvhe versus kvmoff (ratio_dist.py, ratio_rows.py). Boot-to-boot variation on large-working-set sequential rows is therefore larger than the 3.55% figure; the 'vhe' boot is the outlier among the three baselines.
- 'No software cost' is not 'no cost' on the host: in the N90 host CSVs (medians, pkvm vs nvhe) lat_mmap is +18% to +43% (697 vs 487 us at 64 MB), lat_ctx with 8 or more processes +0.7% to +2.8%, lat_proc +1.9% to +2.7%, lat_pagefault +2.0%. The lat_mmap difference is about 0.51 us per touched page (410 touches per iteration), which is in the range of an EL2 round trip, so the N90 data alone cannot exclude a trap per touched page; the exclusion rests on the code and on the June N80 EL2 counter (other kernel, Rust EL2). On the N90 itself only lat_pagefault (+5 ns per fault) argues against EL2 entries on page faults.
- Small unexplained host-side anomaly: random-order rows at 0.375 MB and 0.5 MB are +0.30 ns and +0.63 ns slower under pkvm than nvhe (medians; baseline spread 0.075 and 0.447 ns) while 0.75 to 2 MB show no difference. This is at the 512 KiB L2-cache boundary and is not a TLB effect; the mechanism claims do not explain it.
- For the 2026-09-30 N80 measurements (kernel 6.6.0-79 #93): HEAD adds an SDEI relay, so every host entry into EL2 issues two extra SMCs and SDEI events enter EL2 asynchronously (host.S:43-61,86-103; sdei-relay.c). The June N90 kernel has none of this. It does not change the steady-state read-loop conclusion but should not be projected back onto the N90 runs.
- Scope note for claims 9 and 10: the block-breaking events tied to guests (donation to a protected guest, memcache pages for guest tables) did not occur in the Figure 7 host runs (no VM), and host stage-2 granularity does not govern memory translation inside a guest (the guest has its own stage-2 table and VMID). They must not be used to explain Figure 8.
