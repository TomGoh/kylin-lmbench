## ek#4: refuted (confidence high)

Claim under test: Nothing merges the host stage-2 back into blocks: when a guest page is returned to the host (__pkvm_host_reclaim_page and VM teardown), the page is mapped again for the host as a 4 KiB leaf inside the existing last-level table. The fragmentation of the host stage-2 map caused by a protected VM therefore persists after the VM is gone, until reboot (apart from wholesale unmapping when the host stage-2 page pool is exhausted).

Statement that holds: The host stage-2 map IS merged back into blocks in this kernel. Returning a page goes through host_stage2_set_owner_locked(PKVM_ID_HOST) -> host_stage2_idmap_locked -> kvm_pgtable_stage2_map, whose walker also runs a TABLE_POST callback (stage2_coalesce_walk_table_post). The page is first mapped as a 4 KiB default leaf; then, on the way back up, every table on the path whose page refcount is 1 (no remaining counted entry: no owner annotation, no child table, no non-default mapping) is replaced by a block and freed: the last-level table by a 2 MiB block, and the level-2 table by a 1 GiB block once it holds no table either. A range returned as a whole 2 MiB is replaced by a block directly (TABLE_PRE). So the fragmentation caused by a protected VM lasts while the VM's pages are away and disappears as they are returned (guest pages at teardown through __pkvm_reclaim_dying_guest_page; guest stage-2 tables, memcache pages and the PGD through hyp->host donation). What does persist: (1) tables that existed when EL2 initialisation finished are pinned by pin_host_tables and never merge (on the N80 the slots 0x80000000, 0xc0000000, 0x2080000000 and 0x2340000000 therefore never become 1 GiB blocks); (2) a table that still holds any counted entry, for example a 2 MiB region in which a hyp-heap page has not yet been reclaimed by the host shrinker. Exhaustion of the host stage-2 pool does not unmap RAM: host_stage2_unmap_unmoveable_regs only discards refcount-1 tables in the gaps between memory regions. Safe wording for the paper: 'while a protected VM is running'; not 'until reboot'. This is a source-code result; no measurement on the device after VM exit exists.

## ek#5: partly-correct (confidence high)

Claim under test: The donation size follows the host-side backing of the guest memory: pkvm_mem_abort (arch/arm64/kvm/mmu.c) pins the faulting page and donates PMD_SIZE (2 MiB) at once when the backing folio is at least PMD_SIZE and the memslot alignment allows a stage-2 huge mapping, otherwise one 4 KiB page. Statement that holds: The donation size follows how the VMM itself has the guest memory mapped, not the folio size: pkvm_mem_abort pins the one faulting 4 KiB page and donates PMD_SIZE (2 MiB) at once only when (i) the memslot alignment allows a 2 MiB stage-2 mapping (fault_supports_stage2_huge_mapping) and (ii) the VMM's own page table maps the faulting address with a block of at least PMD_SIZE (get_user_mapping_size walks kvm->mm->pgd); it falls back to one 4 KiB page otherwise, and also when a pinned page already exists inside that 2 MiB range. For a protected VM the page must be swap-backed (anonymous or shmem/memfd), so 2 MiB donations need PMD-mapped THP of that kind; system THP 'always' alone does not give a memfd that. With 4 KiB mappings, host pages are left sharing 2 MiB regions with guest pages. The N80 file is consistent with 4 KiB mappings: 65249 pages present in the VMM's guest-memory mapping, spread over 386 regions (169 per region on average, so at most 127 regions can be completely filled). 'Present in the VMM' is an upper bound for 'donated to the guest'.

## ek#7: confirmed (confidence high)

Claim under test: At EL2 initialisation the host stage-2 identity map is pre-populated for every memory region with the largest aligned block that fits inside the region (1 GiB, else 2 MiB, else 4 KiB). A GiB slot that is not entirely inside one memory region therefore cannot be mapped by one 1 GiB block: on the N80 this applies to the slots at 0x80000000 (94% RAM), 0xc0000000 (87% RAM) and 0x2080000000 (50% RAM). Memory reserved by the kernel (memblock.reserved) is still mapped for the host; memory owned by the hypervisor (its own reserved pool) is not, and splits the blocks around it. State whether the slot at 0x2340000000 (with 368 MB marked reserved in /proc/iomem) can be one 1 GiB block.

Statement that holds: At EL2 initialisation the host stage-2 identity map is pre-populated for every memblock.memory region (NOMAP regions included; the Rust implementation also pre-maps the non-memory gaps) with the largest aligned block that fits inside the region (1 GiB, else 2 MiB, else 4 KiB). A GiB slot that is not entirely inside one memory region therefore cannot be mapped by one 1 GiB block: on the N80 this applies to the slots at 0x80000000 (93.7% System RAM; the rest is a NOMAP region, boundary at 0x84030000), 0xc0000000 (86.6% System RAM, five region boundaries) and 0x2080000000 (50% System RAM, the other half is a NOMAP region, boundary at 0x20a0000000). Their tables exist at the end of init and are pinned, so they never merge later. Memory reserved by the kernel (memblock.reserved) is still mapped for the host; memory owned by the hypervisor (its reserved pool, its image sections, its per-CPU areas, pvmfw) is annotated page by page and splits the blocks around it. ANSWER: the slot at 0x2340000000 cannot be one 1 GiB block. It lies wholly inside the last RAM region and is pre-populated as one 1 GiB block, but the hypervisor's 86 MiB pool sits inside it at 0x237a800000-0x237fdfffff (part of the 366.75 MiB memblock.reserved range 0x2368f40000-0x237fdfffff); fix_host_ownership turns the slot into 469 host 2 MiB blocks plus 43 last-level tables of owner annotations (22016 pages). ## Additional findings

- ek#4 is wrong in a way that changes the narrative: this tree carries the Android coalescing patches (e054adc5821b1, 7517d3cbbaf91; pgtable.c:1127-1176). Running the kernel's own page-table code in a harness, a donated page that is returned restores the original 1 GiB block, and an N80-sized VM (65249 guest pages in 386 regions plus 600 hyp pages) leaves the table bit-for-bit as before once all pages are back. Any text saying the host stage-2 stays fragmented 'until reboot' after a protected VM exits should be removed. One consequence in the paper's favour: a VM that was killed before the June N90 host runs would not have left the host map fragmented, apart from a few hyp-heap pages awaiting the shrinker.
- Experiment S is not a 1 GiB-versus-2 MiB comparison as framed. By the code, a GiB slot holding even one guest-owned or hyp-owned page is mapped by 2 MiB blocks. vm-frames-n80.txt shows guest pages in slots 0x2080000000 through 0x2280000000, and 0x80000000, 0xc0000000, 0x2080000000, 0x2340000000 are pinned at 2 MiB from init. At most 0x22c0000000 and 0x2300000000 could still have been 1 GiB blocks during the evening runs (fewer if hyp metadata or per-CPU pages lie there). In expS.log those two slots are about 2 ns slower, not faster: pick=low 32 MB ns_min 152.3-153.4 (plus two outliers 159.0 and 159.2) against 150.1-151.5 for 0x2140000000-0x2240000000; pick=even 152.9-153.4 against 150.9-151.9; 64 MB 157.1-157.9 against 154.7-156.1. The statement in memlat-rootcause.zh-CN.md line 353 that 2 MiB and 1 GiB blocks are indistinguishable is therefore not established by S, and I cannot say what makes those two slots slower.
- No primary source shows the device's actual host stage-2 table (the kernel exports none). Every statement about which N80 pages sit on 4 KiB leaves is source code plus vm-frames-n80.txt. vm-frames.py counts pages present in the VMM's mapping: for a protected VM a donated page was faulted into the VMM by pin_user_pages (mmu.c:1734), so donated pages are a subset of present pages, but pages the VMM wrote and the guest never touched are counted too. 386 is an upper bound for regions split by guest memory and says nothing about regions split by hyp-owned metadata.
- The 'clear' class of experiments V, V2 and W can contain 4 KiB-mapped regions that vm-frames.py cannot see: guest stage-2 table pages (up to about 512 for this 1 GiB guest), vCPU memcache residue, hyp-heap pages and the hyp per-CPU areas are order-0 kernel pages at unknown addresses, each putting its whole 2 MiB region on 4 KiB leaves. Such contamination would dilute the measured shared-versus-clear difference, not create it.
- NOMAP regions are memory to EL2. The top-level 'reserved' lines of /proc/iomem (64 MiB at 0x80000000, 0.6 MiB at 0xeff50000, 73 MiB at 0xf75f0000, 2.5 GiB at 0x2000000000) are memblock.memory regions copied into hyp_memory and mapped RWX for the host at stage 2. The '% RAM' figures in ek#7 describe System RAM only; slots 0x80000000 and 0x2080000000 are 100% covered by stage-2 memory mappings and miss the 1 GiB block only because a region boundary runs through them. The 86 MiB pool size in the boot log reproduces only with these regions counted (84.26 MiB before alignment, 72 MiB without them).
- The recommendation in memlat-rootcause.zh-CN.md line 369 (back guest memory with 2 MiB pages so host memory does not land in fragmented regions) needs two qualifiers from the code: the 2 MiB donation requires the VMM's own mapping of the address to be a PMD block (get_user_mapping_size), which for a crosvm memfd means shmem THP, not the system-wide 'always' setting the N80 already had; and hyp-owned metadata pages still split some regions, though a 2 MiB-mapped guest needs far fewer stage-2 table pages.
- The parenthesis in ek#4 about pool exhaustion is also inaccurate: host_stage2_unmap_unmoveable_regs walks only the gaps between memory regions and frees only refcount-1 tables; the pool is sized to cover all memory at page granularity (asm/kvm_pkvm.h:334-373). In the harness it left the RAM census unchanged with the VM's pages away.
- Which EL2 implementation produced the June N90 numbers is still unverified on the machine. In-tree evidence points to C, but the N80 kernel has CONFIG_X1_RMS=y while the generic_defconfig that the in-tree packaging rule uses (debian/rules.d/2-binary-arch.mk:23 with flavour 'generic') does not set it at 6.6.0-79.93; shipped kernels are evidently not built from that file, so the N90's /boot/config-6.6.0-73-generic is the only decisive source.
- Limits of my own check: the harness executes verbatim pgtable.c, kvm_pgtable.h, nvhe/mem_protect.c and nvhe/setup.c text with a stub allocator, stub TLB calls, a 40-bit IPA and the N80 memory map; it uses the C host callbacks. The Rust callbacks (host.rs:447-488, consts.rs:141-157, utils.rs:284-331) were compared by reading and found equivalent; they were not executed. Nothing was run on any device.
