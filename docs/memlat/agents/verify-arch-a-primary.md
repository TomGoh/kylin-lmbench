## arch-literature#6: partly-correct (confidence medium)

Claim under test: Item 1f (size of a combined TLB entry). The Arm ARM does not dictate the size at which a TLB stores an entry (it explicitly mentions splintering a page and only requires invalidation to cover at least the size in the translation table entry). A single combined VA->PA entry can be linear only where both stages are single leaf mappings, so it covers at most min(stage-1 size, stage-2 size), further limited to sizes the TLB supports. Consequence for the pKVM host: 4 KiB stage-1 pages over 1 GiB stage-2 blocks give 4 KiB combined entries, i.e. the same TLB reach as native; reach is lost only where stage 2 is finer than stage 1 (for example kernel block mappings over stage-2 regions shattered to 4 KiB).

Statement that holds: Documented: the Arm ARM (DDI 0487E.a) does not dictate the form in which a TLB stores translation table entries (D5.10.2, p. D5-2646), mentions 'splintering a page when caching in the TLB' (D5.10.1 Note, p. D5-2638) and only requires an invalidation to cover at least the size that appears in the translation table entry. Inference, not an Arm ARM rule: one combined VA->PA entry can cover at most min(stage-1 mapping size, stage-2 mapping size), further limited to the sizes the TLB supports; an Arm Ltd patent (US 10,649,907 B2) describes exactly this choice for one design, Bhargava et al. state it for x86, and the Cortex-A53 main-TLB entry records the stage-1 size, the stage-2 level and its own size separately. For the pKVM host, 4 KiB stage-1 pages over 1 GiB stage-2 blocks therefore give 4 KiB combined entries, the same entry size as native. That the TLB reach is the same as native, and that reach is lost only where stage 2 is finer than stage 1, additionally assumes that stage-2-only or intermediate entries take no capacity from the VA->PA entries; this is undocumented for FTC862 and unmeasured (no TLB-miss counts exist for the baseline modes). The N90 data are consistent with unchanged reach (no penalty at 1 to 1.5 MB, +0.13 to +0.21 ns at 2 MB) but do not prove it.

Evidence: Documented inputs, both investigator's copy and independent fetch plus page scans: p. D5-2638 Note 'Where stage 1 information has been cached in multiple TLB entries, as could occur from splintering a page when caching in the TLB, then the invalidation must apply to each cached entry...'; p. D5-2646 'The Arm architecture does not dictate the form in which the TLB stores translation table entries. However, when a TLB maintenance instruction is executed, the minimum size of the table entry that is invalidated from the TLB must be at least the size that appears in the translation table entry.' (the manual says 'form', not 'size'). Patent fetched independently twice from patents.google.com/patent/US10649907B2/en (assignee ARM Ltd, filed 2018-03-22, granted 2020-05-12): 'The final page size will be chosen to be the smaller of the first stage page size and the second stage page size used when determining the address translation data.' (seen through the fetch tool's summariser, same wording both times; it describes an embodiment, not an architectural rule). Bhargava et al. re-fetched (sha256 equal to investigator's), bhargava.txt:215-216 and :175: 'For correctness, the TLB must consider the page size for a given translation to be the smaller of the nested and guest page sizes, referred to as splintering'. Cortex-A53 TRM Table 6-13 (S2 Level [113:112], S1 Size [111:109], Size [58:56]) read in my own download of DDI 0500J (a53-trm-J-nxp.txt:21443-21460) and in the Arm-hosted DDI 0500E. What does not hold as stated: 'same TLB reach as native' and 'reach is lost only where...' are not established for FTC862; Gandhi et al. (cited elsewhere in the same report) observed more TLB misses under nesting on Intel because nested entries share the TLB. Data check (claim11.py): pkvm minus baselines at 1 / 1.5 / 2 MB = -0.04 / +0.07 / +0.17 ns, i.e. no sign of reduced reach, which supports but does not prove the consequence.

## arch-literature#10: partly-correct (confidence high)

Claim under test: Item 5 derivation. Host process with 4-level stage 1 (4 KiB leaf) under a 40-bit, level-1-start stage 2 made of 1 GiB blocks: each stage-2 translation is one descriptor read. (i) No caching at all: 9 references per TLB miss instead of 4, i.e. +5. With a stage-1 walk cache but no stage-2 caching: 3 instead of 1, i.e. +2. With a stage-1 walk cache that stores the physical address of the last-level table but no IPA->PA cache: 2 instead of 1, i.e. +1. (ii) Ideal walk caches (walk cache holding the PA plus an IPA->PA cache hit for the output address): 1 instead of 1, i.e. 0 extra. All extra reads go to the level-1 stage-2 table (8 KiB; at most about 32-34 entries in use on a 32 GiB machine), so each costs roughly one L1 data-cache hit. ## Additional findings

- Wrong file path in the evidence of claim 8: arch/arm64/kernel/idreg-override.c does not exist in the klinux tree (HEAD or tag 6.6.0-73.76). The alias table is in arch/arm64/kernel/pi/idreg-override.c:241-242, the strings are 'kvm_arm.mode=nvhe' and 'kvm_arm.mode=protected' (underscore), and the parser turns '-' into '_' at lines 352-353. The line numbers quoted were right; the path was not.
- An internal document contradicts the kernel code on the kvmoff baseline: docs/n90-kvm-host/kvmoff.md:4, :45-48 says that with kvm-arm.mode=none the host kernel runs entirely at EL1. By the code (no VH override for mode=none, hyp-stub.S:84-99 engages VHE) the kernel stays at EL2 with E2H set, exactly like the 'vhe' boot; 'kvm-arm.mode=vhe' is not even a recognised value (arm.c:2947-2983 returns -EINVAL, which explains the 'Malformed early option' line that vhe.md:61 attributes to duplicated parameters). No raw boot log of the N90 kvmoff boot is in the repository, so its exception level rests on the code reading. Do not quote kvmoff.md for this point.
- Which EL2 implementation was measured in June is not recorded, and the in-tree evidence points to the C one: at tag 6.6.0-73.76 CONFIG_X1_RMS is 'default n' (arch/arm64/kvm/Kconfig:76) and kylinos_generic_defconfig does not set it; it was switched on by commit b1b2979f0c0bf (2026-06-29, 'enable X1 RMS for Rust nVHE and pKVM hibernate', first contained in tag 6.6.0-76.85, not an ancestor of 6.6.0-73.76). The Rust sources at the measured tag are under arch/arm64/kvm/hyp/nvhe/rust/src (byte-identical host.rs, utils.rs, tlb.rs to today's hyp/xhypervisor/src). The N80 device measurements of 2026-09-30 (6.6.0-79, CONFIG_X1_RMS=y) did run the Rust code. The stage-2 geometry is the same in both, but a reply that says the Figure 7 host numbers were measured on the Rust hypervisor needs the kernel config of the N90 image to back it.
- The 40-bit IPA is not a property of 'the FTC862 core type'. Raw boot logs of a Great Wall D80F3 desktop with the same MIDR 0x700f8620 show 'IPA Size Limit: 48 bits' in protected, nVHE and VHE boots (experiments/d3000-pkvm-apps/results/d3000-apps-20260713-111300/pair-1/protected/boot-metadata/dmesg.txt:583 and others), while the N80 logs 40 bits (hw-survey-n80.txt:163). For the N90 the 40-bit value exists only as dmesg lines quoted in docs/n90-kvm-host/{vhe,nvhe,pkvm}.md (:38, :38, :59). With 48 bits the host stage 2 has 4 levels from level 0 and a 1 GiB block costs two stage-2 reads (uncached total 14, +10), so the '+5 / 9 references' figures must be tied to the N90 boot log, not to the core.
- The CPU clock used for ns-to-cycle conversions was probably 1.8 GHz, not 1.9 GHz, on the N90. In the raw N90 reports every simple-operation latency is an integer multiple of 0.5556 ns in all four modes: L1-resident pointer hop 2.223 ns = 4.00 cycles, float/double add 1.110 = 2.00, float/double mul 1.670 = 3.01, integer and float div 4.450 = 8.01, double div 6.670 = 12.0; none is an integer multiple of 0.5263 ns. The header '[MHZ: 1900 MHz, 0.5263 nanosec clock]' is a fixed string in configs/CONFIG.host:7, not a measurement, and the summary files record only scaling limits. Consequences: 7.05 ns is about 12.7 cycles (not 13.4); one 4-cycle read is 2.22 ns; and the 'assumed 4-cycle L1 hit' is in fact what the N90 measures for program loads. (On the N80 the PMU gives 1.903 cycles per ns, so this is specific to the N90 runs.) Confidence medium-high: inferred from seven operation latencies, no PMU cycle count exists for the N90.
- The '7 ns per TLB miss' does not carry over to sequential access. N80 expD.log confirms sequential TLB refills per access equal stride/4096, which would predict +0.44 / +0.88 / +1.76 ns at strides 256 / 512 / 1024 on the N90 at 64 MB; the observed pkvm minus median-baseline differences are -0.01 / +0.22 / +0.38 ns with baseline-to-baseline spreads of 0.54 / 0.41 / 0.59 ns. Any reply should therefore present the 7 ns as the cost seen in the random-page pattern, and explain the near-zero sequential overhead as 'far fewer walks per access and a smaller cost per walk', not as 'no stage-2 cost'.
- Discrimination between 'per TLB miss' and 'per DRAM access' rests on proxies. Using N80 protected-mode PMU rates as stand-ins for the N90, a per-TLB-refill model fits the penalty profile best (R2 0.96) but a fixed extra per L3 refill is not far behind (R2 0.88); at 2-4 MB the penalty per N80-measured refill is about 3.7 ns versus 7.2 ns from 8 MB. No PMU counts exist for the N90 or for nvhe/vhe/kvmoff on any machine, so identical TLB-miss counts across modes are assumed, not measured.
- Mean-based comparisons of the random test are fragile in this data set: every mode has isolated iterations 10-40 ns below its main level from 12 MB upward (e.g. kvmoff 16 MB: 132.4, 134.9, 142.8 against 168.5), so pkvm minus kvmoff by means is +10.3 / +17.3 / +15.2 ns at 12 / 16 / 32 MB against +7.0 / +7.7 / +8.0 ns by medians. The paper's mean-based +3.25% at 64 MB happens to be close to the median-based +3.5%. Internal docs (docs/n90-kvm-host/pkvm.md) also describe an earlier pkvm run ('try1') that dropped to about 154 ns at 64 MB after iteration 4; its raw files are not in results/, so I could not check it, but it shows that a platform state can move this latency by far more than the effect under discussion.
- The Rust and C prepopulation differ: Rust prepopulate_host_stage2 (host.rs:375-409) also identity-maps the MMIO gaps and everything from the top of RAM to 2^ia_bits, the C version (mem_protect.c:155-168) maps memblock regions only. 'About 32-34 level-1 entries in use' is therefore right for entries covering RAM (2 + 30 one-GiB slots on the 32 GiB layout seen in the D80F3 log) and for the C build, not for the populated entries of the Rust build.

The Arm site is script-rendered and returned no body text, so the current issue (chapter D8, rule identifiers) was not checked; an older issue mirrored on GitHub carries the same (S1+1)*(S2+1)-1 note in D4.2.4. A citation in the reply should name the issue explicitly (E.a, D5.2.5, p. D5-2534) or be re-located in the current issue first.
