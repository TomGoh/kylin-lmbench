Runs in the fast random state have no slow 8 MiB samples: noisy nVHE host boot 0/50; day-1/day-2 boots 0 of 21 valid runs at stride 128 (9.05-9.50 ns); the guest run stored as pVM 0/50 (stride 256: 9.87-10.15 ns). Every run in the normal state has them: four clean host boots 93/200; the three non-protected guests 23, 19 and 20 of 50. The reviewer's 'LLC Bnd' item therefore depends on the same unrecorded platform state that produces Figure 8's negative overhead, not only on per-child page placement. None of the claims states this link.
- On the N80 the probe and lmbench's own binary disagree at the same nominal point on the same day: stride 256 at 4 MiB 4.41-4.63 ns (expB) against 4.81-4.95 (expH), at 8 MiB 8.25-9.74 against 10.16-10.51. A later probe run (expR.log, 18:45) still reads 4.46 at 4 MiB, so it is the program, not the hour. Claim 21's conclusions rest on the probe only; it is not an exact stand-in for lmbench.
- Observations that any explanation of the fast state has to fit (raw reports, noisy vs clean nVHE boot): the difference sets in between 2 and 3 MiB in both tests (sequential stride 256 +0.9% at 2 MiB, -7.5% at 3 MiB; random +1.7% and -27.9%); at 4 MiB it depends strongly on stride (-0.8% at stride 64, -9.3% at 128, -7.5% at 256, -1.7% at 512, +13.7% at 1024); and at 12-64 MiB sequential the noisy boot is slower (+4.4..+8.5%). A uniform interconnect-frequency change would not give that pattern by itself.
- Kernel source at the measured version: git show 1e6773d13b560:drivers/devfreq/phytium_noc.c registers the NoC devfreq device with default governor simple_ondemand (line 307), 100 ms polling (line 344) and an 80% up-threshold (line 351). lat_mem_rd times in intervals of at least 100 ms (src/lat_mem_rd.c:143-144, lib_timing.c:173). scripts/apply-masks.sh masks upower and lightdm among its 90 units. Per the docs, every N90 boot in the normal state was booted with these masks and every boot in the fast state predates them or had them incomplete. The NoC state was never recorded on the N90, so this is a lead, not a finding.
- Non-protected guests occasionally produce values at the 'pVM' level: VHE guest 8 MiB iteration 1 = 97.8 ns (pVM run 95.8-101.9; other VHE iterations 123.6-126.6), VHE guest 12 MiB iteration 2 = 130.0 (pVM 127.5-131.6), nVHE guest 12 MiB iteration 9 = 134.9. The low latency is reachable without a protected VM.
- In the clean host boots the slow state at 12-64 MiB is 71% in the vhe boot (47 of 66 samples) and arrives in unbroken episodes: in vhe iteration 3 all 21 DRAM-regime children from stride 32 at 8 MiB to stride 128 at 64 MiB are slow, and in vhe iteration 8 all seven sizes of stride 64. This is a time-varying state of that boot, not independent draws, and it is what makes the VHE bars of Figure 7 negative.
- Differences of a few percent with p < 0.05 between single boots also occur where no page walk is involved: random test at 0.375-0.5 MiB pkvm vs vhe +3.3% and +7.2% (p 0.016 and 0.014), at 0.75 MiB pkvm vs kvmoff and vhe -1.3% and -2.2% (p 0.02 and 0.01). With one boot per mode, a small significant difference is not evidence of a mode effect.
- What the N90 host runs recorded: kernel release, cmdline and scaling_max_freq (bench.sh:53). THP state, ASLR, delivered CPU frequency, devfreq state and running services were printed by prepare-host.sh to the terminal and not stored. The standalone logs carry no metadata at all.
- The benchmark repo changed during verification (HEAD moved from 8b708298 to 58c45b76; new untracked logs). git diff between the two commits is empty for every primary file I used (results/n90-day3-host, n90-day1, n90-day2, standalone-mem-bench, xkernel-n90-*, the N80 expA/B/C/D/L logs and surveys, src, configs, scripts, bench.sh, prepare-host.sh, parse-lmbench.py).
