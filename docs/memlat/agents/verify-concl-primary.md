## concl#6: partly-correct (confidence medium)

Claim under test: [reasoning] The random-access increment cannot be an extra cost per DRAM access: the 64 MB sequential test also fetches a new cache line from memory on every access (stride 256) and shows no increment of comparable size.

Statement that holds: [reasoning] The 64 MB sequential test does fetch a new cache line from beyond L3 on every access (stride 256) and its pkvm increment is about 0.05 ns per access against 6.5 ns for random access, so a non-overlappable cost of several ns per DRAM line fetch is excluded. The test does not exclude a longer latency per DRAM fetch: sequential fetches overlap about 18-fold (10.4 ns per access against 185 ns), which would dilute a 6.5 ns latency increase to at most about 0.4 ns, the size of the spread among the baselines, and at strides 512 and 1024 the sequential increment is as large in relative terms (+2.6%, +3.9%) as the random one (+3.5%). That the increment follows page walks rather than DRAM accesses rests on the size profile of the random test (concl#4), where it is supported but not proven.

Evidence: [H + D] Premises checked. N80 expD.log, sequential 64 MB stride 256: ev2a (L3 refill) 0.985-0.989 per hop, ev2d 0.0625 = 1/16 (one walk per page), ev13 1.00. N90: pkvm median minus mean of kvmoff and nvhe medians = +0.046 ns at stride 256, against +6.50 ns for random 64 MB. Why the step to 'cannot be' does not hold: 10.4 ns per sequential access against 185 ns per random access means about 18 fetches overlap; an added 6.5 ns per fetch would appear as 0.36-0.4 ns at most, equal to the 0.41-0.59 ns spread of the baseline medians. Relative sequential increments vs mean(kvmoff, nvhe): +1.7%, +0.4%, +2.6%, +3.9% at strides 128, 256, 512, 1024. What the data do offer against a per-DRAM-access cost is the random size profile: over 2-64 MB, increment = k x N80 walk rate leaves an RMS residual of 0.71 ns, whereas increment proportional to beyond-L3 latency leaves 1.33 ns and under-predicts 6 and 8 MB by 2.9 and 2.5 ns. No data set varies walks and DRAM accesses independently across modes: the 2 MiB-page run (expC) exists for the N80 in protected mode only.

- Which machine and where each claim's numbers were measured. N90 host with no VM (Figure 7): concl#1, #2, #3, #5, #7, #8. I found no claim that passes a guest number off as a host number or the reverse. Both numbers quoted by the reviewer (3.55%, 3.25%) are host-side Figure 7 numbers; the guest-side Figure 8 data show the opposite sign for random access (about -20%).
- The guest set labelled protected VM carries the full signature of the fast platform state seen in the non-quiesced host set, not just faster random access. Its ten 8 MB stride-256 values are all at the fast level (9.87-10.15 ns), while the three other guests are bimodal with the host's two levels (for example nVHE guest: 12.26 12.36 11.08 10.10 10.31 12.58 12.45 12.38 12.46 12.43). Its 6 MB value is 7.4-7.7 ns against 8.95-9.5 ns in the others (host non-quiesced median 7.46, quiesced 8.2-8.6). It is also the only guest set whose pure-CPU metrics are disturbed: integer divide 4.45 4.46 4.61 4.47 4.45 4.46 4.46 4.47 4.50 4.46 ns, against exactly 4.45 in all 30 reports of the other guests. It was the first guest run (2026-06-05 05:31 UTC); the non-protected pKVM set, whose directory name says 'clean', ran a day later.
- The other three guests also enter the fast state in single runs: VHE guest 8 MB iteration 1 = 97.8 ns (set median 125.0), VHE guest 12 MB iteration 2 = 130.0 (164.4), nVHE guest 24 MB iteration 9 = 153.3 (184.5); ten such runs more than 10% below their own median in total. The fast values are the same as in the set labelled protected VM, so the 20-32% gap in Figure 8 compares two platform states rather than protected against non-protected guests.
- Whether the June N90 measurements ran the Rust EL2 is not recorded and the kernel tree suggests they did not. The host summaries record only kernel=6.6.0-73-generic and the command line. At tag 6.6.0-73.76 (2026-05-15) no file in the tree sets CONFIG_X1_RMS=y and the Kconfig default is n (arch/arm64/kvm/Kconfig:76-81); the option first appears in kylinos_generic_defconfig with commit b1b2979f0c0bf on 2026-06-29 (earliest tag 6.6.0-76.85), after the host runs of 06-03/04 and the guest runs of 06-05/06. docs/n90-kvm-host/SUMMARY.md:41 asserts Rust for the pkvm mode; only the config of the kernel actually installed on the N90 could settle it. The N80 (6.6.0-79) does have CONFIG_X1_RMS=y. The C and Rust paths both pre-populate the host stage-2 in the same way, so the mechanism claims do not depend on this.
- In the N90 host data each mode is a single boot session (uptime in the raw reports runs from about 6 min to 1 h 38 min across the ten iterations), so mode and session are confounded; differences of a few percent between baseline sessions exist (vhe vs kvmoff at 64 MB sequential: +3.6% at stride 512, +5.4% at stride 1024, p < 0.0001). The random-access increment is the one result that holds in a second data set: results/standalone-mem-bench gives pkvm +2.25, +7.31, +6.92, +8.02, +6.86 ns at 4, 8, 16, 32, 64 MB over the median of the three baselines.
- The paper's 'sequential 64 MB overhead only 0.29%' holds for stride 256 only. In the same host data pkvm is +2.7% (stride 512) and +3.5% (stride 1024) above kvmoff by means, both beyond run-to-run noise; vhe is higher still, so this is not evidence of a protected-mode cost, but the statement that sequential access shows no difference at all is specific to one stride.
- The two-level behaviour of sequential latency on the N90 is not confined to 8 MB. At 12 MB, 5 of 40 quiesced runs sit about 20% above the median (stride 256: 13.07-13.78 ns against a median of 11.10), and 0-3 of 40 do at 16-64 MB. The earlier document's statement that neighbouring sizes are unimodal is therefore incomplete.
- N80 PMU event 0x2a (l3d_cache_refill) should not be read as a count of DRAM accesses. At 3 MB random it is 0.41 per hop while the latency is only 28-30 ns against 20-22 ns at 2 MB; if each event were a DRAM fetch the latency would be above 60 ns. Arguments that use this event as the number of memory accesses need that caveat.
- All N80 measurements were taken in protected mode only, so no N80 number can show a difference between modes; every statement of the form 'protected mode costs X per walk' divides an N90 difference by an N80 rate.
- The pkvm try1 host run that earlier documents quote (random 64 MB dropping from 194 to 154 ns at iteration 4) is not in the repository in raw form, in the working tree or in git history; any statement resting on its values cannot be checked from primary data.
