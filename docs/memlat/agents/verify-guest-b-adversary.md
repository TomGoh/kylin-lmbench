## guest-fig8#21: partly-correct (confidence medium)

Claim under test: Evidence-ranked explanations for pVM versus regular VM in random access: (1) a run-level 'fast memory state' of the machine unrelated to protection, which the pVM run was in for its whole 3 hours: strongly supported. Its physical nature is open; sub-candidates are (1a) large-folio backing that survives the top-level THP=never, (1b) physically contiguous versus scattered page allocation on the host (and hence host-contiguous guest memory), (1c) an SoC or memory power/clock state that depends on other activity. (2) pVM-specific stage-2 block mapping: contradicted by code symmetry, by the 4 KiB guest stage 1 and by the guest being faster than bare metal; at most a co-factor worth a few ns. (3) a different guest kernel build for the pVM: contradicted by identical environment.txt and header. (4) mislabelled dataset: cannot be excluded for the label, but the run is not a copy of NP (I/O bandwidth 12-18% lower, page-fault low mode 64 vs 79-81 us) and mislabelling would not explain the speed-up. (5) clock or frequency artefact: excluded.

Statement that holds: Step by step. (1) Evidence: the pVM-labelled run is on the fast curve in 100 of 100 random measurements at 3-64 MB over its 3 hours, even its slowest values are 6-30 ns faster than the KVM-off host medians, and the same curve is present in 10 of 10 iterations of a host-only nVHE run with no pKVM and no guest; predicting pVM = NP minus the host shift leaves a mean error of 3.1 ns. A machine- or run-level fast state that does not need protection therefore explains the pVM advantage: strongly supported. 'Unrelated to protection' goes slightly beyond the data, since with one run per VM type it is not shown whether the way that run was launched induced the state. The physical nature is open and the three sub-candidates are hypotheses; the N80 measurements (another machine) disfavour (1a) large folios and (1b) physical contiguity and leave (1c), a platform clock or power state such as the interconnect frequency, untested but not contradicted. (2) pVM-specific stage-2 block mapping is contradicted by code symmetry and by the guest being faster than bare metal (evidence); the 4 KiB guest stage 1 only excludes larger TLB entries; 'at most a co-factor worth a few ns' is opinion. (3) A different guest kernel build for the pVM is not contradicted by identical environment.txt and header, which carry no build identity; by code the mainline crosvm-platform build cannot boot unprotected, so which builds ran is unknown. A guest build cannot, however, make a guest faster than bare metal. (4) Mislabelling cannot be excluded: the ENV_TAG says NP and no guest metric shows a protection-specific cost. ## Additional findings

- (G, code) An unmodified x-kernel 9bab5da3 crosvm-platform kernel cannot boot as a non-protected guest on the host code of tag 6.6.0-73.76. platforms/aarch64-crosvm-virt/src/init.rs:11-20 calls kvm_guard_granule_init() unconditionally on the boot path (arch/khal/src/mem/mod.rs:49); psci.rs:31-36 asserts that the pKVM MMIO_GUARD_INFO hypercall returns has_range = 1; psci.rs:37-48 panics if an MMIO_GUARD_MAP call fails (used for every device iomap, mm/memspace/src/iomap.rs:128). The host answers these calls only for protected VMs (arch/arm64/kvm/hyp/nvhe/pkvm.c:1559-1621; the non-protected handler at :1629-1644 and arch/arm64/kvm/hypercalls.c:77-105, 277-298, 416-418 return NOT_SUPPORTED with x1 = 0; the Rust EL2 is the same, hyp/nvhe/rust/src/pkvm.rs:3401-3533). The x-kernel developers recorded the same behaviour in April (branch origin/kylin100, docs/crosvm-android-boot-log.md sections 5.2 and 7). So the VHE, nVHE and NP datasets were produced by a guest build that is not mainline 9bab5da3 (no such build exists in any local ref), and whether the pVM-labelled run used the same binary is unknown. Identical environment.txt therefore does not establish 'same guest image', and every code statement taken from 9bab5da3 (scheduler, page size) describes mainline, not necessarily the measured binaries.
- (G) Nothing in the guest data identifies the pVM-labelled run as a protected VM, so its VM type is unverifiable from local sources. Its ENV_TAG and file prefix say NP; across 669 parsed metrics its only deviations from the other three sets are memory-hierarchy speed-ups; its file I/O and file page-fault values are the same two modes as in the other sets, 14-23% faster (x-kernel bounces every virtio request through a once-shared pool in all VM types, io/kdma/src/dma.rs:144-244, so I/O tracks memory speed and shows no protection cost). The claim that its I/O bandwidth is 12-18% lower than NP is a median artefact of bimodal data. docs/EXPERIMENT.md carries a status note dated 2026-06-04 saying protected guests failed to boot on the N90 (that note concerns the earlier Linux-guest attempt), one day before this run.
- (G, Figure 8) The saw-tooth of the two pVM series in the sequential panel below 2 MB is the one-vCPU disturbance of claim 13, not a protection overhead: the mean overhead vs nVHE is +0.40% (+0.26..+0.54) at odd-position sizes and +0.03% at even-position sizes, while NP is +0.02% at both.
- (D, N80: a different machine, protected mode only, no VM) The N80 logs bear on the three sub-candidates for the fast state. With the interconnect governor at performance (nocfreq at 1800 MHz throughout) and 4 KiB pages, lmbench random latency is 152-154 ns at 64 MB and 28 / 35 ns at 3 / 4 MB, at the level of the N90 fast curve (150-153 and 26-36 ns) rather than the N90 normal curve (185-192 and 37-53 ns); at 6-8 MB the N80 values (60-63 and 100-102 ns) lie between the two N90 levels. Physical contiguity changes the 64 MB value by only about 5 ns, and THP also lowers the 1-2 MB values by 3-4 ns, which the N90 fast state does not. This makes a platform clock state (the NoC devfreq device, which has traffic-based governors and is reconfigured by a desktop power service) the leading candidate and large folios or page placement unlikely, but no measurement with a changed governor exists and the N90 governor state in June was never recorded. Absolute N80/N90 comparisons are hazardous: different DIMMs, and the N90 'locked at 1.9 GHz' appears to have run at about 1.80 GHz (L1 load 2.223 ns, against 2.107 ns on the N80 at 1.9 GHz and 1.906 ns on the N90 at 2.1 GHz, all consistent with a 4-cycle L1).
- (H) The sign of the host 'LLC boundary' overhead depends on which stride is picked: at 8 MB, pkvm vs kvmoff/vhe/nvhe is +3.55 / -3.02 / +2.87 % with stride 256 (the one in Figure 7) but -5.00 / -6.46 / -5.83 % with stride 128, because pkvm happens to have 5 low-mode iterations at stride 128 against 2 in each other mode. This supports treating the +3.55% as mode-count noise.
- (lmbench semantics) In lat_mem_rd -t the pages of a working set are the first N entries of a random permutation of all 16384 pages of the 64 MB buffer (src/lib_mem.c:145-152, 254-272), so every working set from 0.5 MB up is scattered over the whole 64 MB of virtual address space. Explanations of the 2 MB threshold in terms of virtual 2 MB regions or page-table locality do not work; what grows with the working-set size is the number of distinct pages and the data footprint.
- (framing error in the investigator's caveats) The prebuilt crosvm in kylin100-xkernel-boots is not from a later snapshot: prebuilt/crosvm has been in that repo since its first commits of 2026-05-19, before the guest runs. Its strings include memfd_create, crosvm_guest, lock-guest-memory and a --hugepages option that neither local launcher passes; whether this binary was the one on the N90 is not recorded.
- (code) Reasoning from HEAD instead of the June tag changes one detail relevant to page placement: at 1e6773d13b560 every guest under pKVM is pinned with FOLL_LONGTERM (arch/arm64/kvm/mmu.c:1705), at HEAD only protected VMs are (mmu.c:1713-1714).
- (docs) The June summary says three sets of raw guest logs are kept although four directories were committed in the same commit; the pVM-labelled set is used only by the ratio tables that feed Figures 8-10.
